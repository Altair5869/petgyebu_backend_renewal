## R-BPFBTK 검토에서 발견된 이슈와 결정

### 이슈 1: 대행사 미확정 (블로커)
F-TEDWWF의 action 슬롯에 "개발을 시작하기 전에 외부 금융 데이터 연동 대행사를 선정하고 지원 범위를 확정한다"는 TODO가 그대로 남아있었음. 대행사가 없으면 dataSpec 스키마, display의 지원 은행 목록, 인증 플로우 방식을 확정할 수 없어 개발 착수가 불가능한 블로커였음.

**결정**: 코드에프(CODEF) API 사용.
**근거**: PRD가 이체 기능을 명시적으로 제외(R-BPFBTK: "잔액 조회나 송금 기능은 포함하지 않는다")했으므로 오픈뱅킹의 이체 기능은 불필요. 마이데이터 직접 라이선스는 자본금 5억 원 이상 + 금융위 인가가 필요해 MVP 단계에 불가능. 코드에프 같은 3rd party 대행사가 오픈뱅킹/마이데이터 API를 재판매하며 조회 전용 연동에 적합.

### 이슈 2: 복수 계좌 선택 로직 누락
description에는 "같은 은행의 여러 계좌를 선택할 수 있다"고 적혀 있었지만 action/dataSpec 슬롯은 단수 계좌 기준으로 좁게 작성돼 있었음.

**결정**: 무제한 허용. 코드에프 API가 은행 인증 1회당 해당 명의 전체 계좌 목록을 배열로 반환하므로 API 레벨에서 이미 복수 계좌가 기본 동작. 가계부 집계 포함/제외 토글은 F-KBBFRU(거래 분류 및 유형 수정)에 배치.

### 이슈 3: 재시도 횟수 불일치
F-OAVYWT(자동 동기화)는 "최대 세 번 자동 재시도"로 명확한데 F-TEDWWF(계좌 연결)는 "재시도 방법을 안내한다"만 있고 횟수가 없었음.

**결정**: 통일하지 않음. 두 기능은 성격이 다름.
- F-TEDWWF: 사용자가 직접 누르는 인증 재시도 → 횟수 제한 없음, 대신 은행/코드에프 측 보안 정책(단시간 반복 시도 차단)을 그대로 안내
- F-OAVYWT: 시스템이 자동으로 도는 백그라운드 재시도 → 기존 3회 + 지수 백오프(1분→5분→15분) 유지

### 이슈 4: successCriteria 측정 기간 모호
"가입 후 계좌 연결 완료율 60% 이상"에 측정 기간이 없었음.

**결정**: 가입 후 24시간 이내를 주 지표로, 7일 이내 누적을 보조 지표로 사용.

## R-CCOEWW 검토에서 발견된 이슈와 결정

### 이슈 1: 자동 카테고리 분류 로직 미정의
R-CCOEWW description은 "기본 카테고리를 자동 지정한다"고 했지만 F-OAVYWT·F-RNECMQ·F-KBBFRU 어디에도 분류 기준이 없었음.

**결정**: 가맹점명 키워드 룰 테이블만 MVP 포함. 매칭 안 되면 "미분류"로 두고 F-KBBFRU에서 사용자가 직접 수정. 뱅크샐러드식 사용자 수정 기반 학습(동일 가맹점명 3~4회 수정 시 자동 학습)은 다음 버전으로 연기.

### 이슈 2: 취소·환불 반영 방식이 "적절히 반영한다"로 모호하게 남아있음
순액 합산인지, 원거래+환불 별도 표시인지, 원거래 취소 처리인지에 따라 예산 사용률(R-JNPAKJ) 계산 결과가 달라지는데 미정의 상태였음.

**결정**: 원거래-환불을 순액(net)으로 소비 지출에 반영. 거래 목록에는 순액만 표시하고, 상세 화면에서 원거래·환불·연결 관계를 확인 가능하도록 함. (이체 매칭과 동일한 데이터 패턴 재사용)

### 이슈 3: 이체 후보 "명확하게 일치" 기준 미정의
**결정**: 금액 완전 일치 + 발생 시각 차이 10분 이내 + 사용자가 연결한 계좌 쌍 사이에서만 자동 연결. 벗어나면 사용자 확인 대상.

### 이슈 4: 90일 초기 수집 범위와 코드에프 실제 지원 범위 미검증
**확인 결과**: 코드에프는 최대 12개월(365일) 이력 조회를 지원하므로 90일은 문제없이 호환됨. 다만 오픈뱅킹류 API는 보통 페이지당 최대 25건 제한이 있어 단일 호출로 90일치가 다 안 돌아올 수 있음.

**결정**: F-OAVYWT action 슬롯에 "페이지 단위로 순차 호출해 90일치를 모두 수집한다"는 구현 힌트 추가.

### 이슈 5: 가계부 제외 계좌의 거래 목록 표시 방식 미정의 (R-BPFBTK 결정 전파 누락)
R-BPFBTK 리뷰에서 F-KBBFRU에 계좌별 가계부 포함/제외 토글을 추가했는데, F-RNECMQ의 거래 목록에 제외된 계좌 거래를 어떻게 보여줄지가 반영 안 돼 있었음.

**결정**: 기본값은 목록에 "집계 제외" 뱃지로 구분 표시. 추가로 설정 페이지에서 계좌별로 "거래 목록에서 완전히 숨김" 옵션도 선택 가능하도록 F-KBBFRU에 하위 옵션 추가.

## R-JNPAKJ 검토에서 발견된 이슈와 결정

### 이슈 1: 기본 임계값 6단계의 실제 퍼센트 구간 미정의
F-VZFPVW rules에는 상태 이름 순서(휴식, 기상, 관심, 불안, 강한 경고, 예산 초과)만 있고 실제 경계값이 없었음. PRD 시나리오는 "기본 임계값을 확인하거나 수정한다"고 해서 기본값 존재를 전제하고 있었음.

**결정**: 아래 기본값으로 확정.

| 상태 | 구간 |
|---|---|
| 휴식 | 0~40% |
| 기상 | 40~60% |
| 관심 | 60~75% |
| 불안 | 75~90% |
| 강한 경고 | 90~100% |
| 예산 초과 | 100%~ |

### 이슈 2: 예산 기간 종료 후 처리 미정의
자동 갱신인지 매번 수동 재설정인지가 없어서, PRD KPI(재방문율 35%, 월간 예산 완료율)와 직결되는 문제였음.

**결정**: 예산 기간 종료 시 동일한 목표 금액과 동일한 상태 구간 설정으로 다음 기간을 자동 생성. 사용자는 언제든 F-FZUVLV에서 수정 가능.

### 이슈 3: 예산 목표 금액 수정 시 소급 적용 여부
수정 시점부터만 반영인지 기간 전체 재계산인지가 없어서 F-EZZFNU(절약 보상) 이력과 충돌할 위험이 있었음.

**결정**: 사용률은 "누적 지출 ÷ 현재 활성 목표 금액"의 실시간 계산값이므로, 목표를 바꾸면 그 즉시 사용률·반려동물 상태가 새 목표 기준으로 다시 계산된다(소급 재계산이 아니라 애초에 실시간 계산이라 자연스럽게 반영됨). 단, 과거 시점에 이미 발송된 알림이나 반려동물 반응 로그 등 "그 시점에 실제로 일어난 이벤트 기록"은 다시 쓰지 않고 그대로 유지한다.

**이월**: 이 계산 방식이 F-EZZFNU(절약 보상) 판정에 미치는 영향은 R-VLQYRM 검토 시 별도로 다룸 (위 "다음 검토로 이월된 항목" 참고).

## R-ENPLNB 검토에서 발견된 이슈와 결정

### 이슈 1: 캐릭터 상태별 에셋(표정/행동) 스펙 부재
F-GGIDHG·F-VZFPVW display에 "행동 또는 표정을 표시한다"고만 있고, 정적 이미지인지 애니메이션인지, 몇 개가 필요한지 정의가 없었음.

**결정**: Lottie(벡터 애니메이션) 방식. 캐릭터 2종(강아지·고양이) × 상태 6단계 = 최소 12개 에셋. iOS/Android/웹 공용 렌더링 가능해서 멀티 플랫폼(PRD devices: 모바일+웹)에 유리. 상태당 3~5초 루프 재생.

**검토했으나 이번 스코프 제외**: 사용자가 화면을 터치하거나 손가락을 옮기면 캐릭터가 시선을 따라오는 반응형 인터랙션. 아이디어는 채택할 만하지만 12개 에셋 전체에 시선 추적용 분리 레이어를 추가하면 제작 공수가 2배 이상 커지고, 경고 단계 애니메이션과 충돌 문제도 있어 MVP 이후 버전으로 보류.

### 이슈 2: 구간 경계값의 포함 기준(inclusive/exclusive) 미정의
R-JNPAKJ에서 확정한 "0~40%, 40~60%..." 표기 그대로는 40%가 두 구간에 동시에 속하는 모순이 있었음.

**결정**: 오른쪽 닫힘 `(시작값, 끝값]`. 즉 경계값과 정확히 일치하면 더 낮은(관대한) 단계로 판정. 0%는 예외적으로 `[0, 40]`으로 처리(지출 없음도 "휴식"에 포함). PRD risk의 "경고 과도 시 이탈" 우려에 맞춰 애매한 경계에서는 관대한 쪽을 택함.

### 이슈 3: "대사" 콘텐츠 자체가 없었음
행동/표정은 상태 이름으로 유추 가능했지만 실제 텍스트 문구가 없었음. 최초 검토 시 "1인칭 대사 + 톤 가이드"로 접근했으나, 논의 중 사용자 제안으로 방향을 "3인칭 상태 묘사"로 전환.

**결정**: 대사체가 아니라 3인칭 관찰형 상태 묘사로 확정. 숫자·전문용어 없음, 사용자를 탓하지 않음 원칙 유지. 톤은 담백한 초안에서 "발랄하고 귀여운" 방향으로 사용자가 직접 조정.

**최종 확정 문구 (6단계)**:

| 상태 | 구간 | 문구 |
|---|---|---|
| 휴식 | 0~40% | 파트너가 이불을 덮고 곤히 잠들어 있어요 |
| 기상 | 40~60% | 파트너가 기지개를 켜며 당신을 바라봐요 |
| 관심 | 60~75% | 파트너가 가계부 옆에 다가와 궁금한 눈으로 지켜봐요 |
| 불안 | 75~90% | 파트너가 걱정스러운 얼굴로 당신 눈치를 살펴요 |
| 강한 경고 | 90~100% | 파트너가 안절부절못하며 당신 곁을 맴돌아요 |
| 예산 초과 | 100%~ | 파트너가 이불 속에 폭 숨어버렸어요 |

원칙 3가지: (1) 숫자·%·원 단위 표기 금지 (2) 3인칭 관찰형("파트너가 ~해요") 통일 (3) 경고 단계에서도 사용자를 탓하는 표현 금지.

*(참고: F-EZZFNU 절약 보상 칭찬 반응 문구는 별개 항목이며 R-VLQYRM 검토 시 같은 톤으로 작성 예정)*

### 이슈 4: 경고 단계 진입 시 능동적 알림(푸시) 여부 미정의
PRD KPI "예산 초과 경고 확인율"은 사용자의 확인 행동이 필요한 지표인데, 기존 정의는 전부 "앱을 열어야만 보이는" 수동적 방식이었음.

**결정**: 푸시 알림 MVP 포함. 단, 6단계 전부가 아니라 **"강한 경고"(90% 진입)와 "예산 초과"(100% 진입) 시점에만, 각 예산 기간당 최초 진입 1회 한정** 발송. 알림 과다로 인한 피로감 방지를 위해 하위 단계(휴식/기상/관심/불안)는 푸시 없이 앱 진입 시에만 노출.

## R-ZHBMMB 검토에서 발견된 이슈와 결정

### 이슈 1: PRD가 요약 화면에 요구한 "기간별 비교"가 F-TKSQSR에 빠져있음
PRD 설명은 요약 화면 구성요소로 "기간별 비교"를 명시했는데, 실제 스펙에서는 비교 기능이 요약 화면(F-TKSQSR)이 아니라 별도 상세 화면(F-IWBASY)으로만 들어가 있었음. PRD 시나리오("출근 전... 먼저 확인한다")를 감안하면 상세 화면까지 들어가지 않아도 비교를 볼 수 있어야 함.

**결정**: F-TKSQSR에 "지난 기간 대비 증감률(%)"을 한 줄로 추가. 형식은 "지난달보다 12% 더 썼어요" 식의 %표시(금액 아님, 예산 목표가 매달 달라질 수 있어 %가 더 일관됨). 비교 대상은 직전 활성 예산 기간. 이전 기간 데이터가 없는 신규 사용자는 이 줄 자체를 표시하지 않음.

### 이슈 2: 주간/월간 자동 집계 전환 기준 미정의
F-IWBASY의 "조회 기간 길이에 맞춰 자동 적용"이라는 문구에 실제 숫자 기준이 없었음.

**결정**: 조회 기간 8주 이하는 주간 단위, 8주 초과는 월간 단위. 4주 기준은 검토했으나 기각 — 월 길이가 4주 또는 5주로 달마다 달라서 "이번 달" 조회가 달에 따라 랜덤하게 주간/월간을 오가는 비일관성이 생김. 8주 기준이면 어떤 달이든 항상 주간 단위로 안정적으로 보임.

### 이슈 3: "주요 지출 카테고리" 노출 개수 미정의
**결정**: 지출 금액 기준 상위 3개 고정 노출. 3개 미만 사용자는 있는 만큼만 표시. 더 보려면 F-IWBASY(카테고리별 분석)로 이동. 동률일 경우 최근 거래가 있는 카테고리 우선.

### 이슈 4: 가계부 제외 계좌 규칙이 F-TKSQSR·F-IWBASY에 전파되지 않음 (R-CCOEWW와 동일 패턴의 누락)
**결정**: 두 기능의 rules에 "가계부 집계에서 제외된 계좌의 거래는 총 지출, 카테고리별 지출, 기간별 지출 집계에서 제외한다. 단, '완전히 숨김'으로 설정하지 않은 경우 거래 목록에서는 여전히 조회 가능하다"를 동일하게 추가. R-CCOEWW → R-JNPAKJ → R-ZHBMMB 세 요구사항이 같은 계좌 제외 규칙을 공유하도록 통일.

## R-VLQYRM 검토에서 발견된 이슈와 결정

### 이월 항목 해소: 예산 목표 인상과 절약 보상 판정의 상호작용
챌린저스(목표에 돈을 걸고 도전하는 앱)류 서비스는 도전 시작 시점에 목표를 고정해 도중에 목표를 낮춰 성공률을 조작하지 못하게 막음. 이 앱은 현금이 아닌 디지털 보상이라 그 정도로 엄격할 필요는 없지만, 판정 기준이 없으면 보상의 의미(진짜 절약했다는 신뢰)가 흐려짐.

**결정**: "목표 예산 이내 지출" 보상 조건은 **예산 기간 시작 시점의 목표 금액을 스냅샷으로 저장**해서 그 값으로 판정. 사용자가 중간에 목표를 올려도 반려동물 상태·사용률 화면은 새 목표 기준으로 즉시 바뀌지만(R-JNPAKJ 결정과 일관), 월말 보상 판정만큼은 원래 목표 기준. "이전 기간 대비 절약" 조건은 목표 금액과 무관하므로 영향 없음.

### 이슈 1: "이전 비교 기간"의 정의 미정의
**결정**: 바로 직전 1개 예산 기간(지난달)과만 비교. 롤링 평균 등은 쓰지 않음. 첫 예산 기간(비교 대상 없음)은 이 조건 평가 자체를 생략.

### 이슈 2: "지출을 줄이면"의 최소 기준 부재
1원만 줄어도 인정되는 상태라 보상 남발 위험이 있었음.

**결정**: 직전 기간 대비 **10% 이상 감소**해야 조건 충족. (5%도 검토했으나 "목표 이내 지출" 조건이 이미 상대적으로 쉬운 경로로 존재하므로, 두 번째 조건은 더 엄격한 10%로 확정)

### 이슈 3: 보상 아이템 목록과 지급 규칙 부재
최초에는 "조건별 고정 아이템 지급(배지+꾸미기 아이템)"으로 검토했으나, 논의 중 방향 전환.

**결정**: **크레딧(인앱 화폐) 지급 후 상점에서 구매하는 방식**으로 최종 확정.
- 목표 예산 이내 지출: 100 크레딧
- 이전 기간 대비 10% 이상 절약: 200 크레딧 (더 어려운 조건이라 2배)
- 두 조건 모두 충족 시 크레딧 합산 지급
- 아이템 가격은 100~500 크레딧 등급으로 구성
- **크레딧은 실제 화폐로 구매 불가** (F-EZZFNU의 "현금성 가치 없음" 원칙을 크레딧에도 동일 적용 — 규제/도박성 논란 방지)
- F-HPWCNJ는 기존 "보관함"(조회 전용)에서 "보관함 + 상점(구매 가능)"으로 역할 확장 필요. 보유 크레딧 잔액 표시 추가.
- 유저플로우 n58(보상 보관함 화면)에 구매 액션 노드 추가 필요

### 이슈 4: 예산 초과 상태와 절약 보상 축하가 동시에 뜨는 UX 충돌 가능성
"이전 기간 대비 10% 절약"은 목표 금액과 무관하게 성립 가능해서, 여전히 예산 초과 상태(반려동물이 "이불 속에 숨음")인데 동시에 보상 축하가 뜨는 모순 상황이 있을 수 있었음.

**결정**: 별도 조율 로직 대신 **이벤트 발생 순서를 명확히 정의**해서 자연스럽게 해소.
1. 예산 기간 종료
2. 새 기간 자동 생성 (R-JNPAKJ 결정: 동일 목표로 자동 갱신)
3. 새 기간 기준으로 반려동물 상태 재계산 (리셋)
4. 절약 보상 판정 (이번 결정: 기간 시작 시점 목표 스냅샷 기준)
5. 보상 있으면 알림 표시

## 계좌 연동 전략 재검토 — 카카오뱅크·토스뱅크 (2026-09-03)

R-BPFBTK 리뷰(2026-08-29)에서 코드에프를 대행사로 확정할 당시엔 지원 은행 목록의 구체적 공백을 몰랐다. 이후 별도 조사에서 코드에프 지원 은행 목록에 **카카오뱅크·토스뱅크가 빠져있다**는 게 확인돼 재검토했다.

### 원인 확인

카카오뱅크·토스뱅크는 웹뱅킹 없는 모바일 전용 구조라 코드에프가 쓰는 스크래핑 방식(개인 인증서·아이디/비밀번호 기반)으로는 연동이 원천 불가능하다. 반면 두 은행 모두 금융결제원 오픈뱅킹 공동시스템 참가기관(카카오뱅크는 2019년 12월 1차 참가, 토스뱅크는 2021년 설립 후 참가)이라, 오픈뱅킹 경로로는 거래내역조회가 가능한 것으로 확인됐다.

### 시장 사례 조사 결과

뱅크샐러드도 동일한 문제를 겪었다 — 2017년 스크래핑으로 출발해 카카오뱅크를 못 다루다가, 2019년 12월 오픈뱅킹 전면 시행에 맞춰 오픈뱅킹으로 카카오뱅크를 보완했고, 이후 2021년 12월 마이데이터로 전면 전환했다. 다만 이 전환은 당시 사용자 약 900만 명·시리즈 D(기업가치 4,400억 원) 규모에서 일어난 일이라, 지금 우리 팀(투자 전, 법인 설립 전) 단계의 벤치마크로 삼기엔 규모 차이가 크다.

반대로 브로콜리(머니랩스)는 오픈뱅킹으로 카카오뱅크까지 확장했음에도 마이데이터 전환에 이르지 못하고 2020년 서비스를 종료했고, 마이데이터 기반 가계부 앱 유플래너도 2026년 서비스를 종료했다(운영사가 같은 해 마이데이터 라이선스를 반납한 것과 무관하지 않은 것으로 판단됨). 헥토데이터(코드에프 운영사)를 포함해 최근 마이데이터 사업자 이탈이 다수 확인됐다 — 다만 헥토데이터는 마이데이터 라이선스만 반납했을 뿐 CODEF 대행 서비스 자체는 계속 운영 중이라, 코드에프를 대행사로 쓰는 우리에게 직접적인 서비스 중단 리스크는 아니다.

### 결정

**v1은 코드에프 단독으로 진행한다.** 카카오뱅크·토스뱅크는 은행 선택 화면(F-TEDWWF)에서 자연스럽게 목록에 없는 상태로 두고, 별도의 "지원 예정 안내"나 "알림 신청" 기능은 넣지 않는다 — 개발 범위를 늘리지 않기 위한 의도적 선택이다. 대신 앱스토어 리뷰, CS 문의 등 이미 들어오는 채널에서 정성적으로 수요를 관찰한다.

**오픈뱅킹 하이브리드 전환은 아래 두 조건이 모두 충족될 때 재검토한다:**
1. 법인 설립 완료 — 금융결제원 오픈뱅킹 이용기관 자격 요건(핀테크산업 분류업종 기업 또는 전자금융업자·전자금융보조업자)이 법인을 전제로 하므로, 이게 충족되기 전엔 이용계약 자체가 불가능하다.
2. 정성적 채널(리뷰·CS 문의)에서 카카오뱅크·토스뱅크 미지원에 대한 불만·요청이 뚜렷하게 확인됨.

오픈뱅킹 조회 전용(잔액조회·거래내역조회만, 이체 API는 신청 안 함) 신청 시 이체 관련 보증보험 의무·보안 심사 부담이 상당히 낮아진다는 것도 확인했다 — 조건 충족 시 실제 착수 부담은 처음 우려했던 것보다 낮다.

### 🔴 블로커 — 엔티티 설계 전에 결정 필수

#### B-1. "예산 기간"의 정의가 어느 문서에도 없다

F-FZUVLV는 "사용자가 예산을 관리할 기간을 설정한다"고 쓰지만, 기간의 단위·시작일·길이 규칙이 정의된 곳이 없다. 월간 고정인지, 사용자가 임의 시작일(예: 급여일)을 고르는지가 미정이다.

이 공백이 다른 확정 사항들과 충돌한다.

- s9 배치(n70→n71→n72)의 실행 시점을 정할 수 없다. 사용자마다 기간 종료 시각이 다르면 전 사용자 대상 일 단위 스캔이 필요하고, 기준 타임존(KST 고정 여부)도 정해야 한다.

#### B-3. 회원 탈퇴·계정 삭제 기능이 없다

### 🟠 MVP 범위 누락

#### M-1. 구매한 꾸미기 아이템을 캐릭터에 적용하는 기능이 없다

F-HPWCNJ는 상점 구매와 보관함 조회까지만 정의한다. 산 아이템을 파트너에게 장착하는 동작이 없고, Lottie 에셋 12개는 상태 6단계용이라 아이템을 어떻게 렌더링할지도 미정이다. 현재 명세대로면 사용자가 크레딧을 모아 아이템을 사도 화면에 아무 변화가 없어, `01-prd.md`가 차별점으로 내세운 재방문 동기가 성립하지 않는다.

결정 필요: 장착 기능을 MVP에 포함할지, 아니면 아이템을 "수집 전용"으로 축소하고 PRD 차별점 문구를 수정할지.

#### M-2. FCM 디바이스 토큰 등록 경로가 없다

`06-sprint-plan.md` Sprint 4에 FCM 발송만 있다. 디바이스 토큰 저장 테이블, 토큰 등록·갱신 API, 알림 권한 요청 UX 노드가 전부 없다. 웹(Next.js) 클라이언트의 푸시 지원 여부도 정해지지 않았다.

#### M-3. 현금 거래를 기록할 수단이 없다

수동 거래 추가·삭제 기능이 없어 계좌 연동으로 수집된 거래만 가계부에 들어온다. 가계부 앱에서 현금 지출이 누락되면 총지출과 예산 사용률이 실제보다 낮게 나온다. 의도적 제외라면 `01-prd.md`에 명시해야 한다.

#### M-4. KPI 계측 공백 2건이 스프린트 플랜에 반영되지 않았다

이 문서의 "01-PRD ↔ 02-기능명세 정합성 점검" 3·4번 항목(자동 분류 출처 플래그, 푸시 발송·열람 로그)이 `06-sprint-plan.md` 체크리스트에 없다. 당시 "개발 착수 전 02에도 반영할지 논의 필요"로 남겨둔 항목이며, 지금이 그 시점이다.

#### M-5. 스프린트 플랜에 테스트와 이벤트 로깅 항목이 없다

Sprint 0~6 체크리스트에 테스트 작성 항목이 하나도 없다. `CLAUDE.md`의 코딩 가이드라인은 작업 전에 검증 가능한 성공 기준을 정의하도록 요구한다. 온보딩 완료율 계측을 위한 이벤트 적재(가입 시각 t=0 기준 24시간·7일 코호트 윈도우 분리)도 이 문서에만 있고 스프린트에는 없다.

#### M-6. 관리자(QUJVUB) 역할의 기능이 하나도 없다

`01-prd.md` 역할 표에 관리자가 있지만 기능명세 12개는 전부 일반 사용자 대상이다. 가맹점명 키워드 룰 테이블과 상점 아이템을 누가 등록·관리하는지 정해지지 않았다. MVP에서 DB 직접 입력으로 처리한다면 그 사실을 명시해야 한다.

### 🟡 확정 사항끼리의 충돌

#### C-1. 환불 거래의 지연 도착과 "기간당 1회 푸시" 규칙이 충돌한다

원거래와 환불 거래가 서로 다른 동기화 사이클에 들어오는 경우가 있다. 90% 진입으로 푸시를 보낸 뒤 환불이 반영되어 사용률이 85%로 내려가고, 이후 다시 90%에 진입하면 F-VZFPVW의 "예산 기간당 1회 한정" 규칙에 막혀 푸시가 나가지 않는다. 재발송 여부 규칙이 없다.

#### C-2. 목표 금액 상향과 "기간당 1회 푸시" 규칙이 충돌한다

R-JNPAKJ 결정 3에 따라 목표 금액을 올리면 사용률이 즉시 내려간다. C-1과 같은 구조로, 이후 다시 경고 구간에 진입해도 푸시가 나가지 않는다. 의도된 동작인지 명시가 필요하다.

#### C-3. 2-way 추가인증 은행은 무인 자동 동기화가 불가능할 수 있다

`06-sprint-plan.md` Sprint 1이 이 리스크를 적었지만 대응이 "DEMO 승인 후 확인"으로만 미뤄져 있다. ARS·앱 승인 등 추가인증이 필요한 은행은 하루 2회 백그라운드 동기화에 사용자 개입이 들어가야 하므로 무인 실행이 성립하지 않을 수 있다. 이는 F-OAVYWT의 Success Criteria인 "수집 성공률 95%"의 근본 리스크다. 스크래핑 방식에서는 은행 사이트 변경, 인증서 만료, 비밀번호 변경이 모두 실패 요인이라 95%는 공격적인 수치다.

대응 방향: 계좌별 "재인증 필요" 상태와 사용자 유도 플로우를 Sprint 1~2 범위에 포함하고, KPI 수치는 DEMO 실측 이후 재조정한다.

#### C-4. 코드에프 API 호출 비용 추정이 없다

호출량은 사용자 수 × 계좌 수 × 하루 2회에 수동 새로고침이 더해진다. `05-infra-stack.md`에 인프라 비용 검토는 있으나 코드에프 호출 과금 검토가 없다. MVP 단계의 비용 리스크로 남는다.

### 결정 기록 (2026-09-15 진행 중)

Q1부터 순서대로 결정한다. 결정이 끝난 항목은 아래에 근거와 함께 기록하고, 전체 완료 후 `02-requirements-features.md`와 `06-sprint-plan.md`에 일괄 반영한다.

#### Q1 ✅ 예산 기간 = 월간 고정, 매월 1일 시작

**결정**: 예산 기간은 매월 1일 00:00(KST)에 시작해 말일 24:00에 종료하는 월간 고정 기간으로 한다. 사용자가 시작일을 고를 수 없다.

**근거**: F-TKSQSR의 확정 문구 "지난달보다 N% 더/덜 썼어요"가 그대로 성립하고, s9 배치 로직이 단순해진다. 달 길이 차이(28~31일)는 남지만 사용자가 직관적으로 이해하는 단위라 F-EZZFNU의 "직전 기간 대비 10% 절약" 판정에서 문제로 인식되지 않는다.

**영향**: BudgetPeriod 엔티티는 `period_start`, `period_end`만으로 충분하다. 급여일 기준 예산 관리는 다음 버전 후보로 둔다.

#### Q2 ✅ s9 배치 = 매일 KST 00:05 전체 스캔

**결정**: 예산 기간 자동 전환 배치는 매일 KST 00:05에 실행하며, 종료 시각이 지난 예산 기간을 모두 찾아 처리한다. 모든 시각 계산의 기준 타임존은 KST로 고정한다.

**근거**: 월 1회 실행(매월 1일)이 비용상 더 싸지만, 매일 스캔 방식은 Q1을 나중에 "사용자 지정 시작일"로 바꾸더라도 배치 코드를 고치지 않아도 된다. 실행 비용 차이는 MVP 규모에서 무의미하다. 분산락은 기존 ShedLock 구성을 그대로 재사용한다.

**영향**: `06-sprint-plan.md` Sprint 6의 Spring Batch Job 항목에 실행 스케줄과 KST 고정을 명시해야 한다.

#### Q3 ✅ 로그인 = 소셜 로그인 전용 (카카오 + 애플)

**결정**: 이메일·비밀번호 로그인을 제공하지 않고 카카오 로그인과 애플 로그인만 제공한다.

**근거**: 비밀번호 저장·이메일 인증·비밀번호 재설정 경로가 전부 사라져 Sprint 0 구현량이 오히려 줄고, 메일 발송 인프라도 불필요해진다. 타겟(20~30대)의 가입 이탈률도 낮다.

**선행 조건 (Sprint 0 착수 전 확인 필요)**:
- 카카오 개발자 애플리케이션 등록 및 동의 항목 설정
- Apple Developer Program 가입(연 $99). iOS 앱이 제3자 소셜 로그인을 제공하면 App Store 심사 지침 4.8에 따라 애플 로그인 병행이 의무이므로, iOS 출시 계획이 있는 한 애플 로그인은 선택이 아니다.
- 웹(Next.js)에도 동일한 두 경로를 붙일지는 Q14(모바일 단독 출시 여부) 결정에 따라 달라진다.

**영향**: User 엔티티는 비밀번호 필드 없이 `provider`(kakao/apple)와 `provider_user_id`를 유니크 키로 갖는다. 같은 사람이 두 경로로 가입했을 때의 계정 통합은 MVP 범위에서 제외하고 별도 계정으로 취급한다.

#### Q4 ✅ 토큰 = 액세스 30분 / 리프레시 14일, 회전 적용

**결정**: 액세스 토큰 만료 30분, 리프레시 토큰 만료 14일. 리프레시 토큰은 사용할 때마다 새로 발급하고(회전) 이전 토큰은 폐기한다. 폐기된 리프레시 토큰의 재사용이 감지되면 해당 사용자의 모든 세션을 무효화한다.

**근거**: 금융 거래 내역을 다루는 서비스의 최소 수준이며 추가 구현 비용이 작다. 기기 등록·관리 화면은 MVP 이후 과제로 둔다.

**영향**: 리프레시 토큰의 폐기 상태를 저장할 곳이 필요하다. Upstash Redis에 TTL 14일로 저장한다(별도 테이블 불필요).

#### Q5 ✅ 회원 탈퇴 = 즉시 전체 삭제

**결정**: 탈퇴 요청 시 해당 사용자의 거래, 연결 계좌, 예산 기간, 상태 구간, 크레딧, 보유 아이템, 동의 기록을 모두 즉시 삭제하고, 코드에프 연결 식별자(connectedId)도 함께 해지한다. 유예 기간이나 복구 경로를 두지 않으며, 탈퇴 화면에서 복구 불가와 재가입 시 처음부터 시작한다는 점을 안내한다.

**근거**: 구현이 가장 단순하고 금융 거래 데이터를 불필요하게 보유하지 않는다. 소프트 삭제 상태 관리와 파기 배치가 모두 필요 없다.

**영향**: `03-user-flow.md` s8에 탈퇴 노드를 추가해야 한다. 코드에프 연결 해지 호출이 실패해도 서비스 측 데이터 삭제는 진행하되, 실패한 해지 건은 재시도 대상으로 기록한다. 신규 기능명세(회원 탈퇴)를 R-BPFBTK 하위에 추가한다.

#### Q6 ✅ 동의 = 가입 시 2종 + 계좌 연결 시 금융 동의 분리

**결정**: 소셜 인증 성공 직후 이용약관과 개인정보처리방침 동의를 받고, 코드에프 제3자 제공 동의와 금융거래정보 조회 동의는 F-TEDWWF의 계좌 연결 시작 직전에 별도로 받는다.

**근거**: 동의를 받는 목적과 그 목적이 실제로 발생하는 시점이 일치해 법적으로 안전하고, 계좌 연결을 아직 시작하지도 않은 가입 단계의 장벽을 낮춘다.

**영향**: `03-user-flow.md`에 동의 노드 2개(가입 직후, 계좌 연결 직전)를 추가한다. 동의 기록은 사용자 식별자, 동의 종류, 동의 버전, 동의 시각으로 저장한다. 약관·개인정보처리방침 문안 자체는 코드 작업이 아니라 별도로 준비해야 하는 선행 산출물이다.

#### Q7 ✅ 카테고리 = 1단계 10개 고정

#### Q8 ✅ 꾸미기 아이템 장착 기능 = MVP 포함

**결정**: 보관함에서 보유 아이템을 선택해 파트너에게 장착·해제할 수 있고, 장착 결과가 메인 홈(F-VZFPVW)의 캐릭터 표시에 반영된다.

**근거**: 이 기능이 없으면 크레딧을 모아 아이템을 사도 화면에 아무 변화가 없어, `01-prd.md`가 차별점으로 내세운 수집·재방문 동기가 성립하지 않는다.

**영향**:
- F-HPWCNJ에 장착·해제 동작과 "현재 장착 중" 상태 표시를 추가하고, 보유 아이템 기록에 장착 여부 필드를 더한다.
- 아이템 에셋은 캐릭터 상태 6단계 애니메이션 위에 겹쳐 그리는 별도 레이어로 제작해야 한다. 상태별 캐릭터 포즈가 달라도 어색하지 않도록 위치·크기 기준을 에셋 제작 단계에서 정해야 하며, 이는 Lottie 에셋 12개 제작과 함께 진행할 선행 작업이다.
- 동시 장착 가능 개수(부위별 1개인지 전체 1개인지)는 아이템 종류를 확정할 때 함께 정한다.

#### Q9 ✅ 푸시 알림 = 모바일 전용

**결정**: FCM 푸시는 Flutter 모바일 앱에만 적용한다. 웹 클라이언트에는 푸시를 구현하지 않고, 웹 사용자는 앱 진입 시 경고 화면으로만 상태를 확인한다.

**근거**: 예산 경고를 즉시 받아야 하는 상황은 대부분 모바일이고, 웹 푸시는 서비스워커 등록·VAPID 키·브라우저별 동작 차이를 별도로 다뤄야 해 비용 대비 효용이 낮다.

**영향**: Sprint 4에 디바이스 토큰 저장 테이블(사용자 식별자, FCM 토큰, 플랫폼, 갱신 시각), 토큰 등록·갱신 API, 앱의 알림 권한 요청 흐름을 추가한다. `02-requirements-features.md` F-VZFPVW의 푸시 규칙에 "모바일 앱 한정"을 명시한다.

#### Q10 ✅ 현금 거래 수동 입력 = 명시적으로 제외

**결정**: 수동 거래 추가·삭제 기능을 MVP에 넣지 않는다. 가계부에 들어오는 거래는 연결 계좌에서 수집한 거래로 한정하며, 이 범위를 `01-prd.md`와 R-CCOEWW에 명시한다.

**근거**: PRD의 핵심 가치가 "수동 입력 부담 제거"라 수동 입력 기능을 전면에 두는 것은 메시지와 충돌한다. 타겟 사용자층의 현금 결제 비중도 낮다.

**영향**: 총지출에 현금 지출이 빠진다는 점은 사용자에게 안내할 필요가 있다. 온보딩 또는 빈 상태 안내에 "연결한 계좌의 거래만 집계된다"는 문구를 넣는다.

#### Q11 ✅ KPI 계측 필드 = 둘 다 MVP 포함

**결정**: 거래 레코드에 최초 분류 출처 플래그(자동 매칭 / 미분류)를 두고, 푸시 알림의 발송과 열람을 로그로 저장한다. 이로써 `01-prd.md`가 계측 공백으로 표시한 "자동 분류 후 수정이 필요한 거래 비율"과 "예산 초과 경고 확인율" 두 KPI를 측정할 수 있게 된다.

**근거**: 두 항목 모두 컬럼 하나와 테이블 하나 수준이라 비용이 작은 반면, 나중에 추가하면 그 전 기간의 데이터를 영원히 확보할 수 없다.

**영향**:
- Sprint 2: Transaction 엔티티에 최초 분류 출처 필드 추가. 사용자가 F-KBBFRU에서 카테고리를 수정해도 이 필드는 덮어쓰지 않는다(최초 값 유지).
- Sprint 4: 푸시 발송 로그(사용자, 예산 기간, 임계값 종류, 발송 시각, 열람 시각) 테이블 추가. 열람 기록은 앱에서 알림 탭 이벤트를 서버로 보내는 방식이므로 Flutter 클라이언트 작업이 함께 필요하다.
- `01-prd.md`의 "⚠️ 계측 데이터 공백" 항목은 이 결정 반영 시 해소 표시로 갱신한다.

#### Q12 ✅ 관리자 기능 = DB 직접 입력으로 대체

**결정**: 관리자 화면과 관리자 API를 만들지 않는다. 가맹점명 키워드 룰 테이블과 상점 아이템 목록은 시드 데이터와 마이그레이션으로 관리한다. `01-prd.md` 역할 표의 관리자(QUJVUB)는 MVP 범위 밖임을 명시한다.

**근거**: 초기 운영에서 룰과 아이템의 변경 빈도가 낮아 배포 주기로 충분하고, 사용자가 없는 단계에서 내부 도구에 스프린트를 쓰는 것은 우선순위가 낮다.

**영향**: 키워드 룰 변경에 배포가 필요하다는 제약이 생긴다. 자동 분류 정확도 개선이 잦아지면 그때 최소 관리자 API를 추가한다.

#### Q13 ✅ 푸시 재발송 = 하지 않음 (기간당 임계값별 1회 엄수)

**결정**: 환불 반영이나 목표 금액 상향으로 사용률이 임계값 아래로 내려갔다가 다시 진입하더라도 푸시를 다시 보내지 않는다. 한 예산 기간 안에서 "강한 경고"(90%)와 "예산 초과"(100%) 푸시는 각각 최대 1회다.

**근거**: 발송 로그의 (예산 기간, 임계값) 유니크 키만으로 보장되어 추가 상태 추적이 필요 없고, R-ENPLNB 결정 4의 알림 피로 방지 원칙과 일치한다. 경계값 근처에서 사용률이 진동할 때 알림이 반복되는 위험도 없앤다.

**영향**: Sprint 4의 Upstash 발송 기록 키(`budget_period_id:threshold`)를 그대로 쓰면 된다. 다만 사용자가 목표 금액을 크게 올려 사실상 새 예산이 된 경우에도 경고를 다시 받지 못한다는 점은 의도된 동작으로 기록해 둔다.

#### Q14 ✅ 출시 플랫폼 = 모바일(Flutter) 단독

**결정**: MVP는 Flutter 모바일 앱으로만 출시한다. 웹은 소개·다운로드 랜딩 페이지만 두고 앱 기능을 구현하지 않는다.

**근거**: 프론트엔드 작업량이 절반으로 줄어 가장 크게 일정을 단축하는 결정이다. Q3(소셜 로그인)과 Q9(모바일 전용 푸시) 결정과도 일관된다. PRD 시나리오의 "출근 전 짧게 확인"도 모바일 전제다.

**영향**:
- `02-requirements-features.md`의 기능 12개에 지정된 디바이스를 "모바일, 웹"에서 "모바일"로 좁힌다.
- `06-sprint-plan.md` 각 스프린트의 프론트 항목에서 웹 화면 작업을 제거한다. Sprint 3의 "lottie 렌더링(웹/모바일 각각)"은 모바일만 남는다.
- `05-infra-stack.md`의 Vercel·Next.js 결정은 랜딩 페이지 용도로 축소된다(구성 자체는 유지).
- 웹 클라이언트는 v2 후보로 남긴다.

#### Q15 ✅ 출시 채널 = 자체 앱으로 MVP 완성 후 재판단 (2026-09-15 추가)

**배경**: Q14에서 Flutter 모바일 단독 출시를 정한 뒤, 앱인토스(Apps in Toss, 토스 미니앱 플랫폼) 선출시 가능성을 검토했다. 조사 결과 자동 계좌 연동 가계부는 이 플랫폼에서 심사를 통과하기 어렵다고 판단했다.

**앱인토스 조사 결과 (2026-09-15)**

| 항목 | 확인 내용 | 우리 결정에 미치는 영향 |
|---|---|---|
| 로그인 | "미니앱에서는 로그인 기능으로 토스 로그인만 쓸 수 있어요. 자사 로그인이나 다른 간편 로그인 방식은 쓸 수 없어요." 사용자 식별자는 앱별로 다른 `userKey`. 동의 항목으로 이름·이메일·성별·생일·휴대폰·CI 선택 수집. **이메일은 null일 수 있다** | Q3(카카오+애플)이 이 채널에서는 성립 불가 |
| 런타임 | React Native 기반 Granite 프레임워크가 주력, WebView도 선택 가능. 빌드 산출물은 `.ait`. **Flutter는 지원 대상이 아니다** | Q14(Flutter 단독)가 이 채널에서는 성립 불가 |

**심사 통과가 어렵다고 본 근거 3가지**

1. 토스가 이미 마이데이터 기반 자동 가계부·자산관리를 자체 제공한다. 핵심 서비스와 직접 겹치고 사용자를 외부 금융 데이터 관리 서비스로 이탈시키는 성격이다.
2. 코드에프 연동은 사용자가 공동인증서나 금융사 ID/비밀번호를 입력해야 한다. 토스 앱 내부에서 외부 대행사 인증창을 띄워 금융 민감정보를 입력받는 구조는 보안 정책상 제한될 가능성이 높다. 런타임이 React Native든 WebView든 이 문제는 동일하다.
3. 앱인토스의 핵심 가치는 "설치와 가입 없는 매끄러운 경험"인데, 토스 로그인 후 외부 금융 인증을 다시 태우면 UX 품질 심사에서 거절 사유가 될 수 있다.

**결정**: MVP는 계획대로 자체 앱(Flutter 모바일 단독)으로 완성한다. 앱인토스를 비롯한 출시 채널 확장은 MVP 완성 이후에 별도로 판단한다.

**근거**: 앱인토스에서 자동 계좌 연동을 포기하면 남는 것은 수동 입력 가계부다. 그런데 `01-prd.md`의 사용자 문제 정의가 "수동 거래 입력 및 분류의 번거로움"이고 솔루션의 출발점이 자동 수집이다. 자동 연동을 빼면 PRD가 풀려던 문제 자체가 사라져 같은 제품의 축소판이 아니라 다른 제품이 된다. 지금 단계에서 채널을 위해 제품 정의를 바꾸는 것은 순서가 뒤바뀐 선택이다.

**영향**: **없다.** Q1~Q14 결정이 모두 그대로 유효하며 문서 재작업이 필요하지 않다. 앱인토스로 전환할 경우에만 Q3·Q9·Q14를 다시 결정하면 된다.

**재검토 시점**: MVP 출시 이후. 그때 판단에 필요한 정보는 위 표에 정리해 두었으므로 재조사 없이 바로 결정할 수 있다. 앱인토스에 실제로 신청하기 전에는 개발자 커뮤니티(techchat)나 문의 채널을 통해 "외부 대행사를 통한 계좌 연동 가계부의 등록 가능 여부"를 먼저 확인해야 한다.

#### Q16 ✅ 꾸미기 아이템 = 캐릭터 장착이 아니라 방 꾸미기, 4슬롯 각 1개 (2026-09-17)

**배경**: Q8에서 "구매한 꾸미기 아이템을 파트너에게 장착한다"로 정했으나, 동시 장착 개수를 정하는 단계에서 방식 자체를 재검토했다.

**문제**: 캐릭터 착용 방식은 아이템 하나가 **캐릭터 2종 × 상태 6단계 = 12개 애니메이션 각각에서 위치가 맞아야** 한다. 잠든 자세, 기지개 켜는 자세, 이불 속에 숨은 자세에서 같은 모자가 전혀 다르게 보인다. 아이템을 하나 추가할 때마다 12번 검수해야 하므로 아이템 종류를 늘리는 비용이 급격히 커진다.

**결정**: 아이템을 캐릭터에 입히지 않고 **반려동물의 방을 꾸미는 방식**으로 바꾼다. 슬롯은 4개이며 각 1개씩 배치한다.

| 순서 | 슬롯 | `item_type` | 설명 |
|---|---|---|---|
| 1 | 벽지 | `WALLPAPER` | 방 배경 |
| 2 | 바닥 | `FLOOR` | 카펫·장판 |
| 3 | 집 | `HOUSE` | 반려동물 집·쿠션 |
| 4 | 장난감 | `TOY` | 소품 |

렌더링 순서는 **벽지 → 바닥 → 집 → 캐릭터 → 장난감**이다. 캐릭터는 집 앞에 앉고 장난감이 가장 앞에 온다.

**근거**

1. **에셋 제작 비용이 크게 줄어든다.** 방 아이템은 캐릭터 포즈와 무관하게 배경·바닥에 놓이므로 12개 애니메이션과의 정합을 맞출 필요가 없다. 캐릭터 애니메이션 12개는 그대로 두고 아이템만 따로 만들면 된다.
2. **수집 동기가 더 강하다.** 갈아입히기는 새 아이템이 이전 것을 대체하지만, 방 꾸미기는 **모은 것이 화면에 동시에 남는다.** 크레딧을 계속 모을 이유가 유지된다.
3. **슬롯 규칙이 단순하다.** 4슬롯 각 1개면 `(user_id, item_type)` 부분 유니크 인덱스 하나로 DB가 보장하고, 렌더링 순서도 슬롯 순서로 고정된다. 아이템끼리 겹치는 위치 문제가 없다.

**비용**: 메인 홈(F-VZFPVW) 화면 구성이 바뀐다. 지금은 캐릭터 + 상태 문구 + 수치 위주인데, 배경·바닥·집 레이어와 그 안에 캐릭터를 배치하는 구성이 필요하다. 다만 아이템마다 12개 애니메이션에 맞추는 작업보다는 훨씬 작다.

**영향**: `01-prd.md` 시나리오 5, `02-requirements-features.md`의 R-VLQYRM 결정 표와 F-HPWCNJ·F-VZFPVW, `03-user-flow.md` n84, `08-feature-implementation-map.md`, `09-db-design.md`를 함께 수정했다. Q8의 "장착 기능 MVP 포함" 결정 자체는 유지되며 대상만 캐릭터에서 방으로 바뀐 것이다.

- API 연동 방식: 코드에프 REST API 기준으로 인증 서버(Java/Python) 설계
