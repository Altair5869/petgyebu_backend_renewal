# 스프린트 플랜: Petgyebu 리뉴얼 MVP

- 갱신: 2026-10-11
- 기준: [리뉴얼 개발 기준](00-renewal-development-guide.md), [기능명세](02-requirements-features.md), [유저플로우](03-user-flow.md)
- 범위: `petgyebu_backend_renewal` 백엔드와 별도 React Native 앱. 기간은 팀 속도에 맞춰 정하며, 각 단계의 완료 조건을 통과한 뒤 다음 단계로 넘어간다.
- 작업 ID: `10-task-backlog.md`의 `M-001`~`M-010`, `APP-001`~`APP-005`(MVP 기준, 이후 F-M07·M-011·APP-006, 과거 월 예산 정정 M-012·APP-007, 카테고리 목표 M-013·APP-008, 달력 보기 M-014·APP-009 추가)와 연결한다. 완료 기준은 해당 백로그와 이 문서, 최상위 기준인 `00`을 함께 따른다.

## 공통 완료 기준

- 백엔드 작업은 입력 검증, 사용자별 데이터 범위, API 응답, 실패 응답을 확인한다. DB 변경은 빈 PostgreSQL에 Flyway를 적용해 검증한다.
- 앱 작업은 iOS·Android에서 정상 흐름과 빈 상태, 로딩, 오류·재시도, 로그인 만료를 확인한다. 사용자가 기록한 지출만 합산한다는 문구와 비난하지 않는 펫 표현을 유지한다.
- 홈·통계는 같은 월 합계 기준을 사용한다. 지출 생성·수정·삭제와 예산 변경 뒤 영향받은 월을 다시 조회한다. 날짜가 월을 넘으면 이전 월과 새 월을 확인한다.
- 변경한 동작에는 의미 있는 테스트를 추가하고 `./gradlew test --no-daemon`을 통과시킨다. 완료 표시에는 백엔드와 앱 각각의 검증 결과를 남긴다.

## Sprint 0 — 기반·계정·세션

**작업:** `M-001`, `M-002`, `M-003`, `M-004`, `APP-001`, `APP-002`; 기능 `F-M01`.

1. 기존 Java 25·Spring Boot 4.1.1·Gradle·Spring MVC·Spring Data JDBC·PostgreSQL·Flyway 구성을 확인한다. 앱은 별도 React Native 프로젝트에서 시작한다.
2. 빈 PostgreSQL에 `users`, `expenses`, `monthly_budgets` 세 테이블의 기준선 마이그레이션을 만든다. 합의한 NOT NULL·FK·UNIQUE·목록 인덱스를 검증한다. 이전 프로젝트 마이그레이션은 복사하지 않는다.
3. 카카오·구글 계정 식별, 서버 자체 액세스·리프레시 토큰 발급, 갱신 시 토큰 교체, 한 계정의 활성 로그인 하나, 로그아웃을 구현한다. `last_login_time`, `active_session_id`, 리프레시 토큰 해시·만료를 사용한다. `device_id`는 넣지 않는다.
4. 내 정보 조회와 회원 탈퇴를 구현한다. 탈퇴는 지출 → 월 예산 → 사용자 순으로 한 트랜잭션에서 삭제한다(이후 `M-013`에서 월 예산 다음에 카테고리 목표 추가). 앱은 두 공급자 로그인, 로그인 유지·만료·재로그인, 로그아웃, 탈퇴 확인을 연결한다.

**완료 조건:** 두 공급자의 동일·다른 계정 식별이 정확하다. 토큰 갱신 뒤 이전 리프레시 토큰이 거부된다. 새 로그인·로그아웃·탈퇴 뒤 이전 액세스 토큰도 거부된다. 다른 공급자는 별도 계정이다. 탈퇴 실패 시 삭제가 모두 롤백된다. 앱에서 정상·실패·만료 흐름을 확인한다. 카카오 액세스 토큰·구글 ID 토큰 확인은 공급자 호출을 가짜 서버로 검증하고, 실제 키로 앱에서 확인하는 일은 별도로 한다. 앱인토스용 토스 로그인은 후속 작업이다.

## Sprint 1 — 펫 선택·수동 지출

**작업:** `M-005`, `M-006`, `APP-003`; 기능 `F-M02`, `F-M03`.

1. `CAT`·`DOG` 선택·변경을 구현한다. 펫 성장·레벨·경험치와 별도 펫 테이블은 만들지 않는다.
2. 지출 생성·단건 조회·월 목록·부분 수정·삭제를 구현한다. 금액은 양의 원화 정수, 날짜는 서울 시간 기준 오늘 또는 과거다. 카테고리 생략·`null` 생성은 `OTHER`, 메모는 최대 100자이며 삭제 시 `memo: null`을 사용한다.
3. 월 지출 목록은 날짜·ID 내림차순 커서 방식으로 기본 20건·최대 50건을 제공한다. 사용자·월이 다른 커서와 잘못된 형식은 `INVALID_CURSOR`로 거부한다.
4. 앱은 펫 선택, 지출 입력·수정·삭제, 확인 대화상자, 빈 목록, 첫·추가 로딩·재시도를 연결한다. 수정 뒤 바뀐 날짜의 월 목록으로 이동하고 목록 커서를 초기화한다.

**완료 조건:** 다른 사용자의 지출 ID는 조회·수정·삭제 모두 404다. 동일한 날짜·금액·카테고리의 중복 지출이 허용된다. 미래 날짜와 수정의 금액·날짜·카테고리 `null`은 거부된다. 메모 삭제 후 목록 제목은 카테고리다. 날짜가 월을 넘으면 이전·새 월의 목록이 일치한다. 마지막 페이지에서 `nextCursor: null`이다.

## Sprint 2 — 필수 월 예산·현재 홈

**작업:** `M-007`, `M-008`, `APP-004`; 기능 `F-M04`, `F-M06`.

1. 사용자·월 예산 조회와 **현재 월에만 허용되는** PUT을 구현한다(MVP 기준. 이후 `M-012`에서 과거 월 PUT 허용). 동시 정상 PUT은 단일 upsert로 한 행을 유지한다. 과거 예산은 조회만 하고 미래 월 예산은 만들지 않는다.
2. 앱은 로그인 → 펫 선택 → 현재 월 예산 설정 → 현재 홈의 필수 흐름을 연결한다. 새 달에는 직전 예산을 입력란에 제안하지만 사용자가 저장하기 전에는 새 달 예산을 생성하지 않는다.
3. DB 지출 합계를 기준으로 현재 월 홈의 예산·지출·사용률·부호 있는 잔액·펫 상태를 계산한다. 상태는 실제 비율에서 50%·80%·100% 경계로 판정하고 사용률 표시값은 소수 첫째 자리에서 버린다. 지출 0건은 안정 상태다.
4. 앱 홈은 펫 상태 → 예산 잔액·사용률 → 지출 기록 순서로 구성한다. 주의는 남은 예산에 집중하는 큰 눈, 경고는 안절부절한 모습, 예산 도달은 멈춘 모습과 빈 게이지로 구분한다. 초과 금액을 별도로 보여주되 펫 상태를 추가하지 않는다.

**완료 조건:** 펫·현재 월 예산이 없으면 홈 진입이 막히고 둘 다 없을 때 펫 선택이 먼저다. 100,000원 예산의 지출 0·30,000·50,000·80,000·100,000·110,000원에서 상태와 잔액이 개발 기준과 일치한다. 실제 49.99%는 표시 49.9%·안정이다. 현재 월 예산을 수정하면 지출 합계는 그대로, 사용률·잔액·펫 상태는 즉시 바뀐다.

## Sprint 3 — 월별 상세 통계·통합 검증

**작업:** `M-009`, `M-010`, `APP-005`; 기능 `F-M05`와 전체 통합.

1. 공통 월 지출 합계로 현재·과거 월의 총액·건수, 카테고리 금액·건수·비중을 제공한다. 비중은 소수 첫째 자리에서 반올림하고, 금액 내림차순·동률 고정 코드 순서로 표시한다.
2. 앱은 월 선택 → 총액·건수 → 카테고리 → 전체 지출 내역 순으로 상세 화면을 연결한다. 카테고리는 일반 세로 스크롤, 지출 목록은 무한 스크롤이다. 현재·과거 빈 월도 고를 수 있지만 미래 월은 고르지 않는다.
3. 지난달을 포함한 과거 월은 숫자만 보여준다. 예산이 없으면 예산·사용률·잔액은 미설정이고 지출 통계는 유지한다. 과거 지출은 수정·삭제할 수 있지만 과거 예산은 수정하지 못한다.(MVP 기준. 이후 `M-012`에서 과거 예산 정정 허용)
4. 지출 생성·수정·삭제, 월 이동, 현재 월 예산 수정 뒤 홈·통계·목록의 값이 일치하는지 통합 검증한다. iOS·Android에서 로그인 → 펫 → 예산 → 홈 → 지출 → 상세 통계 → 로그아웃·탈퇴까지 확인한다.

**완료 조건:** API **15개 동작·11개 고유 경로**(MVP 기준, 이후 `F-M07`로 16개·12개, `F-M08`로 19개·14개, `F-M09`로 20개·15개)와 세 논리 테이블(이후 `M-013`에서 `category_goals` 추가)이 `00`의 계약에 맞는다. 과거 월에 펫 데이터가 없고, 예산 없는 과거 월도 통계가 나온다. 카테고리 정렬·빈 상태·커서 끝·재시도·월 변경 후 첫 페이지 재조회가 확인된다. 외부 금융 연동·보상·푸시 경로는 배포 대상에 없다.

## 출시 전 확인과 후속 실험

- 카카오·구글 공급자 설정, 앱인토스 인증 연동 방식, 이용약관·개인정보처리방침, 실제 배포 환경은 각 담당 단계에서 확인한다. 앱인토스는 토스 로그인만 허용하므로 별도 후속 작업으로 다룬다.
- PostgreSQL 원본 조회로 먼저 정확하게 구현한다. 실제 홈·통계 성능을 측정한 뒤 사용자·월별 **지출 합계만** 캐시하는 실험을 진행한다. 무효화·장애 시 DB 대체·동시 수정 정합성을 검증한 뒤 출시 적용과 제품을 결정한다. 이 실험은 출시 완료 조건이 아니다.
- 스프린트 기간과 인력 배치는 팀 속도에 맞춰 정한다. 작업 ID와 의존 관계는 `10-task-backlog.md`와 일치시킨다. 과거 완료 기록으로 현재 작업을 완료 처리하지 않는다.
