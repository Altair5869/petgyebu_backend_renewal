# 브랜치·PR 전략: Petgyebu 리뉴얼 MVP

- 갱신: 2026-10-11
- 대상: `petgyebu_backend_renewal` 백엔드 저장소. React Native 앱은 별도 저장소에서 같은 검증 원칙을 적용하되 앱의 명령·설정은 그 저장소에서 확인한다.
- 기준: [리뉴얼 개발 기준](00-renewal-development-guide.md), [기능명세](02-requirements-features.md), [스프린트 계획](06-sprint-plan.md), 저장소의 `AGENTS.md`와 `.github/workflows/ci.yml`

## 1. 브랜치 역할

| 브랜치 | 역할 | 들어오는 변경 |
|---|---|---|
| `main` | 출시 후보 검증을 마친 배포 기준 | `develop`에서 검증한 릴리스만 반영 |
| `develop` | 기능을 통합하고 다음 출시를 준비하는 개발 기준 | 기능·수정·문서 PR을 검증한 뒤 반영 |
| 작업 브랜치 | 기능·수정 사항을 작은 단위로 개발 | 최신 `develop`에서 분기하고 `develop`으로 PR |

`develop`도 항상 테스트가 통과하는 상태를 유지한다. 각 스프린트의 기능은 `develop`에서 통합 검증하고, `main`에는 출시 가능한 묶음만 올린다. 현재 저장소에 `develop` 브랜치는 아직 없으므로 이 전략을 적용할 때 `main`을 기준으로 생성한다. 진행 중인 문서 작업 브랜치는 이름이나 작업 내용을 다시 옮기지 않고 이후 `develop`에 통합한다.

## 2. 작업 단위와 브랜치 이름

요청을 기능 ID(`F-M01`~`F-M06`), 백로그 항목, API, 또는 재현 가능한 오류 단위로 나누고 완료 조건을 적는다. 브랜치는 하나의 검토 가능한 변경 단위에 대응시킨다. 한 스프린트에 여러 기능이 있으면 서로 의존하지 않는 기능은 별도 브랜치와 PR로 다룬다. 한 기능에 인증·스키마·화면처럼 검토가 어려운 양의 작업이 모이면 완료 조건이 분명한 작은 PR로 나눌 수 있다.

| 유형 | 이름 | 예시 |
|---|---|---|
| 기능 구현 | `feature/{F-ID}-{영문-슬러그}` | `feature/F-M03-manual-expenses` |
| 기반·설정·문서 | `chore/{영문-슬러그}` 또는 `docs/{영문-슬러그}` | `chore/flyway-baseline`, `docs/renewal-api-contract` |
| 버그 수정 | `fix/{영문-슬러그}` | `fix/monthly-expense-total` |

새 작업 브랜치는 최신 `develop`에서 분기한다. 앱 코드와 백엔드 코드는 각자의 저장소·PR에 기록하고, 한 흐름을 완성하는 작업이면 서로의 PR과 검증 결과를 연결한다.

## 3. 작업 PR에 적을 내용

PR 설명에는 관련 기능 ID·백로그 항목, 사용자가 보게 되는 변화, 변경한 API·DB 계약, 실행한 검증, 남은 미확정 사항을 적는다. 계약이 바뀌면 관련 문서를 함께 갱신한다. 현재 문서가 충돌하면 `00-renewal-development-guide.md`가 우선한다. 이전 검토·문제 해결 기록은 현행 요구사항이나 완료 증거로 사용하지 않는다.

범위 밖인 계좌 자동 연동·배치·푸시·보상·성장 기능을 묶어 넣지 않는다. 캐시는 DB 원본 조회의 성능을 측정한 뒤 별도 실험으로 다루며, 캐시 제품이나 출시 적용을 기능 PR에서 미리 확정하지 않는다.

## 4. 작업 PR의 검토와 병합

1. 작성자는 변경한 동작의 사용자 범위, 입력 검증, 서울 시간대 월 경계, 50%·80%·100% 상태 경계 등 해당 항목의 완료 기준을 검증한다. 스키마 변경은 PostgreSQL·Flyway로 확인한다.
2. 백엔드 PR 전에는 `./gradlew test --no-daemon`을 실행한다. 저장소의 현재 CI는 push와 pull request에서 같은 명령을 실행한다. 앱 PR은 앱 저장소의 빌드·검증 방법을 따른다.
3. 역할을 나누는 기능 개발에서는 `AGENTS.md`에 정의된 구현·독립 검토 역할을 적용한다. 검토자는 기능 요구사항과 API·DB 계약, 실제 테스트 증거를 대조한다. 작성자와 검토자가 같은 파일을 동시에 수정하지 않는다.
4. 검증과 검토가 끝난 작업 PR을 **`develop`에 squash merge**해 작업 단위 커밋 하나로 남긴다. 병합 후 작업 브랜치는 삭제한다. `develop`과 `main`은 모두 빌드·테스트 가능한 상태로 유지한다.

GitHub의 squash 허용, 병합 후 브랜치 자동 삭제, `develop`·`main` 보호 및 필수 검사 설정은 이 문서만으로 적용 여부를 확인할 수 없다. 실제 저장소 설정을 확인해 적용하며, 설정 전에도 위 병합 절차를 따른다. 과거 저장소의 설정 기록으로 현 저장소의 상태를 단정하지 않는다.

## 5. 출시 PR과 태그

출시 후보를 정하면 `develop`의 대상 커밋을 고정하고 [스프린트 계획](06-sprint-plan.md)의 해당 완료 조건과 백엔드·앱 흐름을 검증한다. 출시 PR을 검증하는 동안에는 새 기능을 `develop`에 병합하지 않는다. 개발을 계속해야 하면 그 커밋에서 릴리스 브랜치를 만들어 검증하고, 그곳에서 발생한 수정은 출시 뒤 `develop`에도 반영한다.

검증된 `develop` 또는 그 커밋에서 분기한 릴리스 브랜치를 `main`으로 보내는 **출시 PR은 일반 merge commit으로 병합**한다. 작업 PR의 squash 이력을 유지하면서 검증한 커밋 계보가 `main`에 포함되도록 하기 위해서다. 출시 후 `main`의 결과를 `develop`에도 반영해 다음 작업의 기준을 맞춘다. 출시 PR에는 포함한 기능·검증 결과·알려진 제한과 함께 검증한 앱 버전·커밋을 적는다.

태그는 스프린트 완료 자체가 아니라 `main`에 검증된 출시 후보가 병합된 뒤 `v0.{N}.0` 형식으로 남긴다. 태그는 배포 기준점을 표시하며 실제 배포 완료를 뜻하지 않는다.

## 6. 커밋과 완료 기록

커밋과 작업 PR 제목은 Conventional Commits 형식(`feat:`, `fix:`, `chore:`, `docs:` 등)을 사용한다. 작업 PR의 squash merge 시 제목이 최종 커밋 메시지가 되므로 변경의 목적을 한 문장으로 적는다. 출시 PR 제목은 포함한 버전을 식별할 수 있게 적는다. 백로그 완료 표시는 새 MVP 계약과 해당 PR·검증 결과를 확인한 뒤 갱신한다. 이전 제품의 완료 표시를 그대로 옮기지 않는다.
