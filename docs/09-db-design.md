# DB 설계: Petgyebu 리뉴얼 MVP

- 갱신: 2026-10-11
- 기준: [리뉴얼 개발 기준](00-renewal-development-guide.md), [기능명세](02-requirements-features.md), [구현 맵](08-feature-implementation-map.md)
- 대상: PostgreSQL 16, Spring Data JDBC, Flyway
- 상태: 새 빈 DB에 적용할 논리 설계와 기준선 DDL. 3절 DDL은 `src/main/resources/db/migration/V1__baseline.sql`로 적용했다(`M-002`).

## 1. 관계·소유권·저장 범위

```text
users (1) ──< expenses (N)
     └──────< monthly_budgets (N, 사용자·월마다 최대 1건)
```

논리 테이블은 **`users`, `expenses`, `monthly_budgets` 세 개**다. 지출과 월 예산은 사용자 ID로 소유권을 확인한다. 펫 종류는 `users`에 저장하지만 펫 상태·성장·월 지출 합계·사용률은 저장하지 않는다. 별도 펫·세션·집계·환불·변경 이력 테이블도 MVP에 두지 않는다.

외래 키는 유지하고 `ON DELETE CASCADE`는 사용하지 않는다. 회원 탈퇴는 애플리케이션이 **지출 → 월 예산 → 사용자** 순서로 한 DB 트랜잭션에서 명시적으로 삭제한다. 실패하면 모두 롤백한다. Spring Data JDBC에서는 지출·예산을 사용자 객체의 컬렉션으로 묶어 자동 삭제시키지 않고 각자 ID로 다룬다.

## 2. 테이블과 필드

### `users`

| 컬럼 | PostgreSQL 타입 | DB 제약·의미 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK |
| `provider` | `VARCHAR(10)` | NOT NULL; `KAKAO` 또는 `GOOGLE`는 앱 검증 |
| `provider_user_id` | `VARCHAR(255)` | NOT NULL; 공급자가 해당 사용자에게 부여한 ID |
| `pet_type` | `VARCHAR(10)` | NULL 허용; 선택 후 `CAT` 또는 `DOG` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL; 가입 시각 |
| `last_login_time` | `TIMESTAMPTZ` | NOT NULL; 마지막 소셜 로그인 성공 시각 |
| `active_session_id` | `UUID` | NULL 허용; 현재 로그인 식별자, 로그아웃 시 비움 |
| `refresh_token_hash` | `VARCHAR(255)` | NULL 허용; 현재 리프레시 토큰의 해시. 원본 저장 금지 |
| `refresh_token_expires_at` | `TIMESTAMPTZ` | NULL 허용; 현재 리프레시 토큰 만료 시각 |

`UNIQUE(provider, provider_user_id)`로 공급자 계정 중복을 막는다. `provider_user_id`가 카카오·구글에서 부여한 ID이며 같은 뜻의 별도 `provider_id`는 두지 않는다. 이메일은 식별자나 UNIQUE 키로 사용하지 않는다. 같은 사람이 두 공급자를 쓰면 두 계정이다. `active_session_id`는 설치·기기 ID가 아니며 `device_id` 컬럼은 MVP에 두지 않는다.

사용자는 소셜 로그인 성공 시 생성되므로 `last_login_time`을 함께 기록한다. 새 로그인은 세션 ID와 리프레시 토큰 해시·만료를 교체한다. 갱신은 현재 해시와 만료를 검증한 뒤 새 값으로 교체한다. 인증 요청은 토큰의 세션 ID가 현재 행의 `active_session_id`와 일치해야 한다. 로그아웃은 세 세션 관련 컬럼을 비우고, 탈퇴는 사용자 행까지 삭제한다. `UUID`와 해시 컬럼 길이는 내부 구현 선택이며 외부 토큰 형식을 정하지 않는다.

### `expenses`

| 컬럼 | PostgreSQL 타입 | DB 제약·의미 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK |
| `user_id` | `BIGINT` | NOT NULL; `users.id` FK |
| `amount` | `BIGINT` | NOT NULL; 1원 이상 1억 원(100,000,000) 이하 원화 정수는 앱 검증 |
| `expense_date` | `DATE` | NOT NULL; 사용자가 기록한 지출 날짜 |
| `category` | `VARCHAR(20)` | NOT NULL; 일곱 카테고리 중 하나는 앱 검증 |
| `memo` | `TEXT` | NULL 허용; 앱·서버에서 최대 100자 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL |

같은 사용자·날짜·금액·카테고리의 여러 지출은 허용한다. 중복 방지 UNIQUE는 두지 않는다. 생성 시 `category`를 생략하거나 `null`로 보내면 애플리케이션이 `OTHER`로 바꿔 저장한다. 메모 생략·빈칸·공백만 입력은 `null`이다. 수정의 `memo: null`은 삭제이고, 금액·날짜·카테고리의 명시적 `null`은 오류다. 2000-01-01부터 오늘까지의 날짜만 허용하며 ‘오늘’은 `Asia/Seoul`로 판단한다. 이 규칙은 DB `CHECK`가 아니라 요청·서비스 검증으로 지킨다.

월별 목록 정렬과 커서 조회를 위해 **`(user_id, expense_date DESC, id DESC)`** 인덱스를 둔다. 목록은 사용자·월 범위를 먼저 제한하고 날짜·ID 내림차순으로 조회한다. 같은 날짜에서 ID가 안정적인 이어보기 순서가 된다.

### `monthly_budgets`

| 컬럼 | PostgreSQL 타입 | DB 제약·의미 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK |
| `user_id` | `BIGINT` | NOT NULL; `users.id` FK |
| `budget_month` | `DATE` | NOT NULL; API의 `YYYY-MM`을 해당 월 1일로 변환 |
| `amount` | `BIGINT` | NOT NULL; 1원 이상 1억 원(100,000,000) 이하 원화 정수는 앱 검증 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL |

`UNIQUE(user_id, budget_month)`로 사용자·월 예산을 한 행으로 제한한다. `budget_month`는 연도를 포함한 날짜이지 월 번호만이 아니다. 현재 월 예산만 생성·수정한다. 과거 예산은 조회만 가능하고 미래 예산은 미리 저장하지 않는다. 새 달에는 직전 금액을 앱 입력란에 제안하되 사용자가 저장하기 전에는 행을 만들지 않는다. 월 첫날 정규화는 애플리케이션에서 검증하며 DB `CHECK`를 두지 않는다.

동시 정상 PUT은 다음과 같은 **단일 upsert**로 처리한다. 이 유일성 충돌은 앱에 재시도용 409를 주는 사유가 아니다.

```sql
INSERT INTO monthly_budgets (user_id, budget_month, amount, created_at, updated_at)
VALUES (:userId, :firstDay, :amount, :now, :now)
ON CONFLICT (user_id, budget_month)
DO UPDATE SET amount = EXCLUDED.amount, updated_at = EXCLUDED.updated_at
RETURNING *;
```

## 3. 기준선 DDL (`V1__baseline.sql`)

```sql
CREATE TABLE users (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  provider VARCHAR(10) NOT NULL,
  provider_user_id VARCHAR(255) NOT NULL,
  pet_type VARCHAR(10),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_login_time TIMESTAMPTZ NOT NULL,
  active_session_id UUID,
  refresh_token_hash VARCHAR(255),
  refresh_token_expires_at TIMESTAMPTZ,
  CONSTRAINT uq_users_provider_identity UNIQUE (provider, provider_user_id)
);

CREATE TABLE expenses (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  amount BIGINT NOT NULL,
  expense_date DATE NOT NULL,
  category VARCHAR(20) NOT NULL,
  memo TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_expenses_user_date_id
  ON expenses (user_id, expense_date DESC, id DESC);

CREATE TABLE monthly_budgets (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  budget_month DATE NOT NULL,
  amount BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uq_monthly_budgets_user_month UNIQUE (user_id, budget_month)
);
```

이 DDL은 합의한 PK·NOT NULL·FK·UNIQUE·인덱스를 반영한다. 금액 양수, 카테고리·펫 종류·공급자 값, `budget_month`가 첫날인지 같은 업무 규칙을 위한 DB `CHECK`는 없다. `created_at`·`updated_at`의 기본값은 INSERT에만 작용하므로 애플리케이션은 수정 시 `updated_at`을 갱신한다. `last_login_time`은 로그인 성공 처리에서 명시적으로 기록한다.

## 4. 집계·커서·캐시

월 경계는 `Asia/Seoul`의 `[월 첫날, 다음 달 첫날)`이다. `expense_date >= :firstDay AND expense_date < :nextMonthFirstDay AND user_id = :userId`로 지출 범위를 제한한다. 합계·건수는 `COALESCE(SUM(amount), 0)`과 `COUNT(*)`로, 카테고리 통계는 같은 범위를 `GROUP BY category`로 계산한다. 지출 0건이면 0원·0건과 빈 카테고리 배열이다.

예산 잔액은 `budgetAmount - spentAmount`이며 초과 시 음수 그대로 반환한다. 사용률의 표시값은 소수 첫째 자리에서 버리지만 펫 상태는 버리기 전 비율로 판정한다. 카테고리 비중은 소수 첫째 자리 반올림이다. 월 예산이 없는 월(통계의 현재 월 포함)은 예산·사용률·잔액만 `null`이고 지출 통계는 계산한다. 과거 월에는 펫 상태를 계산·저장하지 않는다.

지출 목록 커서는 사용자·월에 묶고, 잘못된 형식·다른 월의 커서는 400 `INVALID_CURSOR`로 거부한다. 앱은 월이나 지출 내역이 바뀌면 커서를 폐기하고 첫 페이지부터 조회한다. 커서 인코딩과 토큰 형식은 외부 계약을 지키는 범위에서 구현 시 정한다.

월 합계는 우선 DB 원본으로 조회한다. 이후 성능을 측정해 사용자·월별 지출 합계만 캐시하는 실험을 할 수 있다. 지출 생성·수정·삭제가 확정된 뒤 영향받은 월의 캐시를 무효화하며 날짜가 월을 넘으면 두 월을 무효화한다. 예산 변경은 지출 합계 캐시를 바꾸지 않는다. 캐시 장애 시 DB 조회로 동작한다. 펫 상태와 홈 응답 전체는 캐시하지 않는다.

## 5. 마이그레이션과 검증

- Flyway 기준선은 새 빈 PostgreSQL에 위 세 테이블만 만든다. 이전 제품의 17개 테이블 마이그레이션을 복사하거나 기존 운영 DB를 자동 변경하지 않는다.
- 필수 DB 제약·인덱스와 동시 예산 PUT의 한 행 유지, 탈퇴 트랜잭션의 롤백, 다른 사용자의 지출 접근 차단을 통합 테스트한다.
- 금액·카테고리·미래 날짜·월 첫날 정규화는 애플리케이션 테스트로 검증한다. 직접 SQL 또는 운영 마이그레이션은 이 검증을 우회하므로 별도 확인한다.
- 월 집계는 월말·연말과 서울 시간대 경계, 지출 날짜가 다른 월로 이동하는 경우를 검증한다. 캐시를 실험하면 동시 수정과 장애 시 DB 원본과의 일치 여부를 추가 확인한다.
