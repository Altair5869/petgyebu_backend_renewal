# 카테고리별 목표 금액·카테고리 지출 목록 설계

- 작성: 2026-10-28
- 기준: [리뉴얼 개발 기준](../../00-renewal-development-guide.md), [Service 규칙 구조](2026-10-27-service-rules-refactor-design.md), [소비 인사이트](2026-10-27-spending-insights-design.md)
- 범위: 백엔드 API만 다룬다. 앱 화면은 후속 작업이다.

## 1. 의도

사용자는 어디에 가장 많이 썼는지 보고, 예를 들어 "이번 주는 카페를 줄여야겠다"처럼 행동을 바꾸고 싶어 한다(사용자 발언). 지금은 줄여야 할 카테고리를 알아도 그 다짐을 숫자로 정해 둘 곳이 없다. 늘어난 카테고리의 실제 지출을 골라 볼 방법도 없다.

- **카테고리별 목표 금액:** 예를 들어 "카페는 이번 달 5만 원까지"처럼 정한다. 정한 카테고리마다 쓴 금액, 남은 금액, 사용률을 본다.
- **카테고리 지출 목록:** 그 달 지출 목록을 한 카테고리로 걸러 본다. 예를 들어 "왜 카페가 늘었지?"를 확인하는 단계다.

사용자 결정:

- 목표는 **달마다 따로** 정한다. 다음 달로 이어지지 않는다.
- 한 달의 목표 합은 **그 달 전체 예산을 넘을 수 없다**. 목표를 넣거나 고칠 때 막는다.
- 전체 예산을 목표 합보다 낮추는 것은 **허용**한다. 이때 조회 응답에 초과 상태를 내려 앱이 알려 주게 한다.
- 목표는 **지울 수 있다**. 예산 삭제 기능은 여전히 없다.
- 두 기능을 함께 진행하고, 이번에는 **백엔드 API까지만** 만든다.

## 2. 목표·비목표·실패 조건

목표

- 사용자·월·카테고리별 목표 금액을 설정·변경·삭제한다.
- 한 달의 목표와 각 목표의 사용 현황을 조회한다.
- 월 지출 목록을 카테고리 하나로 걸러 조회한다.

비목표

- 목표 이월·자동 생성, 목표 추천, 목표 초과 알림·푸시.
- 펫 상태를 카테고리 목표로 판정하는 것(펫 상태는 지금처럼 전체 예산 기준이다).
- 홈·통계·인사이트 응답 변경.
- 여러 카테고리를 한 번에 거르는 필터.
- 앱 화면.

실패 조건

- 동시 요청 두 개가 각각 검사를 통과해 목표 합이 예산을 넘는다.
- 다른 사용자의 목표나 지출이 보이거나 바뀐다.
- 예산을 낮춘 뒤의 초과 상태를 조회 응답에서 알 수 없다.
- 탈퇴 뒤 목표 행이 남거나, FK 때문에 탈퇴가 실패한다.
- 카테고리 필터를 붙였을 때 정렬·커서·`limit` 규칙이 필터 없는 목록과 달라진다.

## 3. 데이터

새 테이블 `category_goals`를 만든다(마이그레이션 `V3`).

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | |
| `user_id` | `BIGINT NOT NULL REFERENCES users(id)` | `ON DELETE CASCADE` 없음 |
| `goal_month` | `DATE NOT NULL` | 해당 월 1일, `budget_month`와 같은 규칙 |
| `category` | `VARCHAR(20) NOT NULL` | `Category` 7개 값. DB `CHECK` 없음 |
| `amount` | `BIGINT NOT NULL` | 1 이상 1억 이하는 애플리케이션에서 검증 |
| `created_at`, `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |

- `UNIQUE(user_id, goal_month, category)`를 둔다. 같은 사용자·월·카테고리의 목표는 한 행이다.
- 이 기능으로 논리 테이블이 3개에서 4개가 된다. `AGENTS.md`의 "3개 논리 테이블" 문구와 `00`·`09`의 테이블 설명을 함께 고친다.
- 탈퇴 시 삭제 순서는 지출 → 월 예산 → **카테고리 목표** → 사용자다. 같은 트랜잭션에서 지우며, FK 재시도 규칙(최대 3회)은 그대로 둔다.

## 4. API

모든 엔드포인트는 인증이 필요하다. 인증이 없으면 기존과 같은 401 `UNAUTHORIZED`다. `{month}`는 예산과 같이 2000-01부터 서울 기준 현재 월까지만 받는다. 그 밖의 값은 400 `INVALID_REQUEST`(`month`)다.

### 4.1 `GET /api/v1/months/{month}/category-goals`

```json
{
  "month": "2026-10",
  "budgetAmount": 500000,
  "goalTotalAmount": 150000,
  "goalsExceedBudget": false,
  "goals": [
    {"category": "CAFE", "goalAmount": 50000, "spentAmount": 32000, "remainingAmount": 18000, "usagePercent": 64.0}
  ]
}
```

- `goals`에는 목표가 있는 카테고리만 `Category` 선언 순서(FOOD, CAFE, TRANSPORT, SHOPPING, HEALTH, LIVING, OTHER)로 담는다. 목표가 없으면 빈 배열이다.
- `spentAmount`는 그 달 그 카테고리 지출 합계다. 통계의 카테고리 `spentAmount`와 같은 값이다.
- `remainingAmount = goalAmount - spentAmount`이며 음수일 수 있다. 음수면 그 절댓값만큼 초과한 것이다.
- `usagePercent`는 홈·통계와 같은 규칙으로 계산한다. 소수 첫째 자리에서 버리며 100을 넘을 수 있다(`BudgetUsage`와 같은 계산).
- `goalTotalAmount`는 목표 금액의 합이다. 목표가 없으면 0이다.
- `budgetAmount`는 그 달 예산이고, 없으면 `null`이다.
- `goalsExceedBudget`는 예산이 있고 `goalTotalAmount > budgetAmount`일 때만 `true`다. 예산이 없으면 `false`다.
- 예산은 지울 수 없고 목표는 예산이 있어야 만들 수 있다. 따라서 예산이 `null`인데 목표가 있는 경우는 없다.
- 예산·목표가 없어도 200이다. 펫 선택은 요구하지 않는다.

### 4.2 `PUT /api/v1/months/{month}/category-goals/{category}`

- 요청 본문은 `{amount}`이다. 금액 검증은 예산과 같다(`RequestBodies.amount`). 1 이상 1억 이하 정수가 아니면 400 `INVALID_REQUEST`(`amount`)다.
- `{category}`가 7개 값이 아니면 400 `INVALID_REQUEST`(`category`)다. 대소문자는 지출 생성과 같은 규칙을 따른다.
- 검사 순서는 `month` → `category` → 본문(객체·`amount`) → 예산 존재 → 합계 한도다.
- 그 달 예산이 없으면 409 `BUDGET_REQUIRED`다. 코드는 같지만 메시지는 그 달 예산을 가리킨다. 예: "이 달 예산을 먼저 설정해야 합니다."
- `(다른 카테고리 목표 합) + amount > 예산`이면 409 `CATEGORY_GOALS_EXCEED_BUDGET`이고 행은 바뀌지 않는다. 합이 예산과 같으면 허용한다.
- 성공하면 생성·변경 모두 200 `{month, category, amount}`이다. 같은 행을 교체하며 `created_at`은 유지하고 `updated_at`만 갱신한다.
- 예산이 이미 목표 합보다 낮아진 상태에서도 위 규칙을 그대로 적용한다. 따라서 목표를 줄이는 변경이라도 결과 합이 예산을 넘으면 막는다. 이런 상태는 목표 삭제나 예산 증액으로 풀 수 있다(제 판단: 규칙을 하나로 유지한다).
- **동시성:** 한도 검사와 저장을 한 트랜잭션에서 한다. 먼저 그 사용자·월의 예산 행을 `SELECT … FOR UPDATE`로 잠근 뒤 목표들을 읽고 저장한다. 같은 사용자·월의 목표 PUT은 이렇게 하나씩 처리되며, 두 요청이 모두 통과해 한도를 넘는 일이 없다. 예산 PUT은 목표를 검사하지 않으므로 잠금을 추가하지 않는다.
- 탈퇴와 겹쳐 사용자 FK 위반이 나면 예산 PUT과 같이 401이다.

### 4.3 `DELETE /api/v1/months/{month}/category-goals/{category}`

- 204를 반환한다. 목표가 없어도 204다(제 판단: 결과 상태가 같으므로 멱등으로 둔다).
- `month`·`category` 검증은 PUT과 같다. 예산이 없어도 400·409를 내지 않는다.
- 다른 사용자의 행은 `WHERE user_id`로 건드리지 않는다.

### 4.4 `GET /api/v1/months/{month}/expenses?category=CAFE`

- 기존 목록에 선택 파라미터 `category`를 더한다. 없으면 지금과 똑같이 동작한다.
- 있으면 그 카테고리 지출만 같은 정렬(날짜 내림차순, 같은 날짜는 ID 내림차순), 같은 `limit`(기본 20, 최대 50), 같은 커서 형식으로 돌려준다.
- 잘못된 값이면 400 `INVALID_REQUEST`(`category`)다.
- 커서에는 카테고리를 넣지 않는다. 정렬 키가 같으므로 커서는 위치 표식으로 그대로 유효하다. 앱은 필터를 바꾸면 기존처럼 커서를 버린다(제 판단).
- 인덱스는 기존 `ix_expenses_user_date_id`를 그대로 쓰고 새로 만들지 않는다. 한 사용자의 한 달 행을 대상으로 거르는 조건이 하나 늘 뿐이다.

## 5. 구조

[Service 규칙 구조](2026-10-27-service-rules-refactor-design.md)를 따른다. DB는 행 조회와 동시성 경계만 맡고, 계산은 도메인 객체가, Service는 이름 붙은 규칙을 맡는다.

- 새 패키지 `goal`에 컨트롤러·서비스·요청 record·리포지토리·도메인 객체를 둔다.
- 목표 사용 현황은 도메인 객체에서 계산한다. 입력은 목표 행 목록과 `ExpenseRepository.findAmounts`(이미 있음)로 읽은 그 달 지출 행이다. 카테고리 합계는 `MonthlySpending`을 재사용한다. DB 없이 단위 테스트할 수 있어야 한다.
- 한도 검사(`validate…` / `require…`)는 Service의 이름 붙은 규칙으로 둔다. 합계 계산은 도메인 객체가 한다.
- 목표 저장은 `ON CONFLICT (user_id, goal_month, category)` upsert다. 예산 잠금 조회는 `MonthlyBudgetRepository`에 잠금 전용 메서드로 추가한다.
- 카테고리 필터는 `ExpenseRepository`에 카테고리 조건이 있는 첫 페이지·다음 페이지 조회를 추가하거나, 기존 쿼리에 선택 조건을 넣어 처리한다. 방식은 빌더가 고른다.
- 탈퇴 시 `UserService.withdraw`가 새 리포지토리의 `deleteAllOfUser`를 예산 삭제 다음, 사용자 삭제 앞에 호출한다. 예산을 먼저 지우면 탈퇴가 목표 PUT이 잡은 예산 행 잠금에서 먼저 기다리므로, 목표 행과 예산 행을 서로 반대 순서로 잠그는 교착 상태가 생기지 않는다.

## 6. 검증

- **단위 테스트(도메인 객체):**
  - 목표가 있는 카테고리만 선언 순서로 나온다.
  - 지출이 없는 목표는 0원·0%다.
  - 초과하면 잔액이 음수이고 사용률이 100%를 넘는다.
  - 사용률 버림이 적용된다(예: 49.99 → 49.9).
  - 목표 합과 `goalsExceedBudget`의 경계가 맞다(같음은 `false`, 1원 초과는 `true`, 예산 없음은 `false`).
- **API 테스트(Testcontainers):**
  - 응답 필드 집합.
  - PUT으로 생성한 뒤 같은 행을 교체한다.
  - 합이 예산과 같으면 허용하고, 1원 넘으면 409이며 행이 바뀌지 않는다.
  - 예산이 없으면 409 `BUDGET_REQUIRED`다.
  - 예산을 낮춘 뒤 GET이 `goalsExceedBudget: true`를 내고, 이어지는 목표 PUT은 409다.
  - DELETE는 204이고 없는 목표도 204다.
  - 잘못된 `month`·`category`·`amount`는 400이고, 검사 순서를 지킨다.
  - 과거 월에 목표를 넣을 수 있고, 미래 월은 400이다.
  - 다른 사용자의 목표는 보이지 않고 바뀌지 않는다.
  - 미인증 요청은 401이다.
  - 같은 사용자·월에 서로 다른 카테고리 목표 PUT을 동시에 보내도 목표 합이 예산을 넘지 않는다.
  - 탈퇴하면 목표 행이 0건이 된다.
  - 카테고리 필터는 해당 카테고리만 정렬·커서 순서대로 돌려준다. 다른 사용자 지출은 제외되고, 잘못된 값은 400이며, 필터가 없으면 기존과 같다.
- `./gradlew test --no-daemon` 전체가 통과해야 한다. PR 전에 qa-engineer 검토를 받는다.
