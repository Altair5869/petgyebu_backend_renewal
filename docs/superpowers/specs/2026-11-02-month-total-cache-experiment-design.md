# 월 합계 캐시 실험 설계 (2026-11-02)

## 1. 의도

출시 전에 "캐시 없이도 홈·통계가 충분히 빠른가"를 데이터로 판단한다. 지금 느리다고 느낀 화면은 없다. 결과물은 두 가지다.

1. 월 합계 캐시를 출시에 넣을지 말지 정할 수 있는 측정 결과와 결론
2. 측정에서 드러난 캐시 외 성능 개선(근거가 있을 때만)

기준 문서: `docs/00-renewal-development-guide.md` 9절, `docs/05-infra-stack.md` 4절, `docs/09-db-design.md` 4절. 캐시는 **사용자·월별 지출 합계만** 대상이며 홈 응답 전체·펫 상태는 캐시하지 않는다. 캐시는 출시 필수 조건이 아니다.

## 2. 배경

- 2026-10-25 기준선과 2026-10-27 비교(`perf/results/`)에서 DB 쿼리는 모두 1ms 미만, HTTP p95는 홈 14ms·통계 12~19ms, heavy 홈 약 25ms였다. 앱·DB·k6가 한 Mac에서 돌아 DB 왕복 비용이 사실상 0이었다.
- 출시 계획은 Cloud Run(서울, `--max-instances=2`) + Supabase Free(서울, session pooler)다. 요청마다 DB까지 네트워크 왕복이 생기므로, 쿼리 시간보다 **요청당 DB 왕복 횟수 × 왕복 지연**이 응답 시간을 좌우할 가능성이 높다. 캐시가 줄이는 것도 주로 이 왕복이다.
- 월 합계는 #35 이후 `ExpenseRepository.findAmounts` 행을 `MonthlySpending`이 서비스에서 합산한다(사용자 결정, 유지). 홈(`HomeService`)은 합계만 쓰고, 통계·카테고리 목표·인사이트는 카테고리별 금액도 쓴다. 따라서 "합계만" 캐시하면 직접 이득은 **홈**에 한정되고, 통계 등은 행 조회가 그대로 남는다.

## 3. 목표 / 비목표 / 실패 조건

목표
- 출시 환경을 흉내 낸 조건(DB 왕복 지연 주입)에서 캐시 없는 현재 코드의 홈·통계 p95를 잰다.
- 요청당 DB 왕복 횟수를 엔드포인트별로 센다.
- 캐시의 최대 효과(상한)를 같은 조건에서 잰다.
- 아래 판단 기준으로 채택 여부를 결론 낸다.

비목표
- Redis 등 외부 캐시 서비스 도입, 배포, Cloud Run·Supabase 실측
- 월 집계 테이블·스냅샷·비동기 집계·배치(문서상 MVP 밖)
- 대규모 부하·용량 계획

실패 조건(기술적으로 돌아가도 실패)
- 측정 중 노트북 메모리가 부족해 다른 작업이 멈추거나, 측정 볼륨·컨테이너가 남는다.
- 캐시가 사용자·월 값을 섞거나, 무효화·장애 상황에서 DB 원본과 다른 값을 응답한다.
- 실험용 캐시 코드가 채택 결정 없이 `develop`에 들어간다.

## 4. 제약

- **소규모**: 노트북 메모리가 부족하다(현재 여유 약 40%). 사용자 200명 × 12개월. `seed.sql`의 등급 규칙(id 기준, heavy = 100의 배수)상 heavy는 2명(uid 100, 200)이다. 지출 약 10만 건 안팎.
- 메모리 상한(기준값, 빌더가 조정 가능): 측정 DB tmpfs 512MB, `--shm-size=256m`, 앱 JVM `-Xmx512m`. 측정 후 `docker rm -f -v`로 반드시 정리한다.
- 동시 사용자(VU) 10, 워밍업 10초 + 측정 30초(기존 `perf/k6/baseline.js` 방식). 스크립트 기본값이 `USERS=1000`, `VUS=20`이므로 `-e USERS=200 -e VUS=10`을 넘긴다. heavy는 토큰 2개(uid 100, 200)를 VU 10명이 나눠 쓴다. `perf/README.md`의 컨테이너 예시(`--shm-size=1g`, tmpfs 2g)도 이 상한에 맞춰 고친다. create·mixed처럼 데이터를 바꾸는 시나리오는 마지막에만 돌리거나 다시 시드한다.
- k6 summary의 `setup_data`(토큰)는 커밋 전에 지운다. 비밀값을 결과에 남기지 않는다.
- 새 런타임 의존성을 `develop`에 추가하지 않는다. 측정 도구(지연 프록시 컨테이너 등)는 측정 절차에만 쓴다.

## 5. 판단 기준 (사용자 승인, 수치는 Claude 제안)

1. 지연 주입 조건 B(왕복 2ms)에서 홈과 통계(이번 달·지난 달)의 서버 응답 p95가 **50ms 이하**면 캐시 없이 충분하다.
2. 캐시는 아래를 **모두** 만족할 때만 출시 적용을 제안한다.
   - 1번 기준을 넘는 시나리오가 있다.
   - 그 시나리오에서 캐시로 p95가 **30% 이상** 줄어든다.
   - 정합성 검증(6.4)을 통과한다.
3. **계산 먼저 (사용자 결정):** 6.2의 왕복 수와 조건 B 측정으로 "합계 캐시가 없앨 수 있는 최대 비율"(캐시가 없애는 왕복·쿼리 시간 ÷ 전체 응답 시간)을 먼저 계산한다. 이 상한이 30% 미만이면 6.3 캐시 구현과 6.4 정합성 검증을 생략하고 **비채택**으로 결론 낸다. 30% 이상이 가능할 때만 6.3·6.4를 진행한다.
4. **캐시 외 개선 (사용자 결정):** 기존 결정과 충돌하지 않는 개선(인덱스, 커넥션 풀 크기, 같은 결과를 내는 조회 수 감소 등)은 측정 근거가 확인되면 개별 PR로 적용한다. 기존 결정을 바꾸는 개선(월 합계를 SQL `SUM`으로 되돌리기 — #35 결정, 인증의 세션 확인 흐름 변경 — 보안 동작)은 결과 문서에 근거와 함께 **제안만** 하고, 사용자가 하나씩 승인한 뒤에 PR한다. 이 제안을 위해 원인 분리 측정(예: 행 수별 `findAmounts` vs `SUM` 비교)은 해도 된다.
5. **판정 방법 (Claude 결정):** 결론에 쓰는 시나리오는 **3회** 반복하고 **중앙값** p95로 판정한다. 조건 B 5ms는 민감도 확인용으로 기록만 하고 판정에는 쓰지 않는다. 다만 5ms에서 50ms를 넘는 시나리오가 있으면 결과 문서에 위험으로 적는다.

## 6. 실험 구성

### 6.1 측정 조건

- 기준선 조건 A: 지연 없음(기존 방식, 비교용).
- 출시 흉내 조건 B: 앱과 DB 사이에 TCP 지연 프록시를 두고 **DB 왕복마다 약 2ms**(한쪽 1ms씩) 지연을 더한다. 같은 서울 리전 가정이다. 시간이 허락하면 5ms도 한 번 잰다(리전 밖·풀러 지연이 큰 경우 감도 확인).
- 시나리오: normal·heavy × home, stats_current, stats_past. 필요하면 insights·category goals 추가.
- 노이즈가 크므로(지난 측정에서 같은 조건 재측정 차이가 큼) 비교는 한 세션 안의 쌍만 쓰고, 결론에 쓰는 시나리오는 최소 2회 반복한다.

### 6.2 요청당 DB 왕복 수

엔드포인트별로 한 요청이 DB에 보내는 문장 수(인증의 `hasActiveSession` 포함, 트랜잭션 `BEGIN/COMMIT` 포함 여부를 명시)를 센다. 방법은 빌더가 정한다(예: 측정 DB에서 `pg_stat_statements` 호출 수 차분, 또는 JDBC 로깅). 결과 표에 "왕복 수 × 주입 지연 ≈ 지연으로 늘어난 시간"을 함께 적어 해석한다.

### 6.3 캐시 상한 실험

- 목적은 **캐시 효과의 상한**을 재는 것이다. 제품 선택(Redis 등)은 채택이 정해질 때 한다.
- 실험 브랜치에서만, 프로세스 내 맵(새 의존성 없이) 기반의 사용자·월 지출 합계 캐시를 켜고 끌 수 있게 만든다. 끈 상태가 기본이다.
- 적용 범위: 홈의 월 합계. 키는 (사용자 id, 월). 값은 합계(long).
- 무효화: 지출 생성·수정·삭제 트랜잭션 커밋 후 해당 사용자·월 무효화. 수정으로 날짜가 다른 월로 가면 두 월 모두. 예산 변경은 무효화하지 않는다. 회원 탈퇴 시 해당 사용자 항목 제거.
- 장애 대체: 캐시 조회·저장이 실패하면 DB 조회 결과로 응답한다(실험에서는 실패를 강제로 일으키는 스위치로 검증).
- 측정: 같은 조건에서 캐시 ON(적중 상태) vs OFF p95 비교.

### 6.4 정합성 검증 (5절 3번에서 진행하기로 했을 때만)

상한 실측 단계(Claude 결정)에서는 아래 중 경쟁 조건 항목(동시 수정)을 제외한 나머지를 테스트한다. 실험 코드는 머지하지 않으므로 맵 캐시와 커밋 후 단순 무효화로 충분하다. 실측 결과 채택을 제안하게 되면, 경쟁 조건 테스트까지 포함한 전체 검증을 별도 설계·PR에서 한다.


- 생성·수정(같은 월/다른 월로 이동)·삭제 직후 홈 합계가 DB 원본과 같다.
- 사용자 A의 캐시가 사용자 B 응답에 섞이지 않는다. 같은 사용자의 다른 월이 섞이지 않는다.
- 동시 수정: 무효화와 조회가 겹칠 때 오래된 값이 남지 않는다(조회가 무효화 이전 값을 캐시에 다시 넣는 경쟁 포함).
- 캐시 장애 스위치 ON에서 응답이 DB 원본과 같다.
- 월 경계(서울 시간대 말일·1일).
- **알려진 한계**: Cloud Run 인스턴스가 최대 2개라 프로세스 내 캐시는 인스턴스 간 무효화가 안 된다. 채택을 제안하게 되면 이 문제의 해결책(공유 캐시, 인스턴스 1개 고정 등)은 사용자 결정 사항으로 넘긴다.

## 7. 결과물

1. `perf/results/2026-11-xx-cache-experiment.md`와 원본 출력 디렉터리(EXPLAIN, k6 JSON — `setup_data` 제거). 환경·조건·왕복 수·표·해석·결론(채택/비채택 + 근거)을 담는다.
2. `perf/README.md`에 지연 주입 절차 추가(재현 가능하게).
3. 결론에 따라 `docs/00` 9절 후속 결정 표, `docs/05` 4절, `docs/10` 출시 준비 표의 캐시 항목을 갱신한다.
4. 캐시 실험 코드는 **채택되지 않으면 머지하지 않는다**. 브랜치는 기록용으로 남기거나 결과 문서에 핵심 diff 요약만 남긴다. 채택이면 별도 설계·PR로 다시 진행한다.
5. 캐시 외 개선은 근거가 측정으로 확인된 것만 5절 4번 규칙에 따라 낸다. 후보(확인 전): 트랜잭션 왕복, 통계의 조회 수, 커버링 인덱스 `INCLUDE(amount, category)`, Hikari 풀 크기 — 바로 PR 가능. 요청마다 도는 `hasActiveSession` 조회 흐름 변경, 월 합계 SQL `SUM` 복귀 — 제안만.
