# 2026-11-02 월 합계 캐시 실험 결과

> **결론: 월 합계 캐시는 채택하지 않는다.** DB 왕복 약 2ms를 주입한 조건에서 홈·통계 6개 시나리오의 p95 중앙값이 모두 50ms 이하(최대 normal home 42.00ms)라서 판단 기준 1(캐시 없이 충분)을 만족한다. 캐시 효과의 상한(월 합계 조회를 아예 생략한 스텁)은 같은 시간대 비교에서 normal 23.7%, heavy 40.3%였다. heavy는 30%를 넘지만 기준 2의 첫 조건(50ms를 넘는 시나리오가 있다)을 만족하지 않으므로 캐시 구현(스펙 6.3)과 정합성 검증(6.4)은 하지 않았다. 왕복 약 5.2ms에서는 home이 50ms를 넘어(normal 56.18, heavy 51.11ms) **위험으로 기록**한다.

스펙: `docs/superpowers/specs/2026-11-02-month-total-cache-experiment-design.md`
원본 출력: `2026-11-02-cache-experiment/statements/`(요청당 DB 문장), `2026-11-02-cache-experiment/latency/`(지연 확인 `select 1` 시간), `2026-11-02-cache-experiment/k6/`(k6 summary JSON, `setup_data` 제거), `2026-11-02-cache-experiment/upper-bound-stub.diff`(스텁 코드)

## 환경

- 장비: Apple M2, 16GB. Docker Desktop 28.5.1(8 CPU·약 7.7GB). 앱·DB·프록시·k6를 한 대에서 실행했다.
- 소프트웨어: Java 25.0.4.1, PostgreSQL 16(tmpfs `size=512m`, `--shm-size=256m`, `pg_stat_statements`), toxiproxy `ghcr.io/shopify/toxiproxy:2.12.0`, k6 v2.3.0. 앱은 `bootTestRun`(가짜 로그인) `-Xmx512m`, 포트 8090, 프록시(55433) 경유.
- 데이터: `perf/seed.sql` `-v users=200 -v months=12`(사용자 200명, 지출 93,600건, 예산 2,400건). 시드는 `setseed(0.42)`로 결정적이다. normal은 월 30건(uid 10–59, 50명), heavy는 월 300건(uid 100, 200).
- k6: `perf/k6/baseline.js`, `-e USERS=200 -e VUS=10`, 워밍업 10초 + 측정 30초. create·mixed는 돌리지 않았다(데이터 불변).
- 앱 코드:
  - 기준(`base_*`, `recheck_*`): `src`가 develop(`064b5db`)과 같은 커밋(`9be0b9b`, `f430a6d`).
  - 스텁(`stub_*`): 로컬 브랜치 `experiment/month-total-upper-bound`(`3f66571`, push·머지하지 않음). `petgyebu.perf.skip-month-total=true`이면 `HomeService.home`이 `findAmounts`를 부르지 않고 `spent = 0`으로 둔다. 시작 후 heavy 사용자 `/home`의 `spentAmount`가 0임을 확인했고, 재측정용 앱(플래그 끔)에서는 7,484,000으로 돌아온 것을 확인했다.
- 세션: 앞서 시작한 측정이 Docker 종료로 끊겨 측정 DB가 사라졌다. 같은 시드로 다시 만들고 Task 3 기준 측정 30회를 한 세션에서 처음부터 다시 했다. 실행 순서는 기준(0ms → 2ms 3회 → 5ms) → 스텁 2ms 3회 → 기준 home 2ms 재측정 3회다. 시드는 한 번만 했다.

## 지연 확인 (`select 1` 5회의 절대 시간, ms)

| 조건 | toxic 설정 | 측정 | 중앙값 |
| --- | ---: | --- | ---: |
| 0ms | 0 | 0.29, 0.40, 0.17, 0.19, 0.14 | 0.2 |
| 2ms | 1 | 2.83, 2.72, 1.95, 2.17, 3.17 | 2.7 |
| 2ms (스텁 측정 직전) | 1 | 1.57, 1.76, 1.89, 1.88, 2.21 | 1.9 |
| 5ms | 4 | 5.85, 5.57, 4.75, 5.22, 4.58 | 5.2 |

각 행은 그 조건의 첫 시나리오 직전에 잰 값이다(`latency/0ms.txt`, `2ms.txt`, `2ms-stub.txt`, `5ms.txt`). 표의 값은 기본 왕복(약 0.2ms)을 포함한 절대 시간이며, 지연 없음 대비 증가분은 2ms 약 2.5ms, 5ms 약 5.0ms다. 같은 toxic 설정이라도 실행마다 1ms 안팎 흔들린다(2ms 2.72 vs 1.88). `perf/README.md`의 보정값(`set 1` 약 2.0, `set 4` 약 5.3ms)은 다른 시점의 8회 측정이다. 아래에서 "2ms", "5ms"는 조건 이름이다.

계획·스펙과 다른 점: 지연은 양방향 분할(계획) 대신 보내기 방향 한쪽에 toxic 값 전체를 걸었다(`perf/latency.sh` 주석: 방향마다 타이머 오차가 더해짐). 효과 상한은 스펙 5.3의 계산식(없어지는 왕복 ÷ 전체, 약 2 ÷ 40ms ≈ 5%) 대신 계획대로 스텁 실측을 썼고, 실측 쪽이 더 큰(엄격한) 상한을 준다.

## 요청당 DB 문장 (지연 0, `statements/README.md`)

| 엔드포인트 | 요청당 조회 | 트랜잭션 | 추정 왕복 |
| --- | ---: | ---: | ---: |
| home | 4 (세션 확인, 사용자, 이번 달 예산, `findAmounts`) | 2 (인증 필터, 서비스) | 약 6 |
| stats_current, stats_past | 3 (세션 확인, 그 달 예산, `findAmounts`) | 2 | 약 5 |

요청당 문장 수는 Docker 종료 전 앞선 세션(같은 시드)에서 쟀다. 측정 시간은 계획(워밍업 0초·10초)과 달리 워밍업 1초·5초였고, 파일 머리에 k6 요청 수 대신 `hasActiveSession` 호출 수(= 인증된 요청 수)로 비율을 확인했다.

PostgreSQL JDBC 드라이버가 `BEGIN`을 첫 조회와 같이 보내므로 왕복은 트랜잭션마다 "조회 수 + `COMMIT` 1"로 추정했다. 월 합계 캐시가 적중하면 home에서 `findAmounts` 1개 왕복과 그 행의 전송·매핑이 없어진다.

## 지연 조건별 부하 (캐시 없음, `http_req_duration{phase:measure}`, ms)

판정 조건 2ms는 3회의 p95와 중앙값이다.

| 시나리오 | 0ms p95 | 2ms p95 r1 / r2 / r3 | **2ms 중앙값** | 5ms p95 |
| --- | ---: | --- | ---: | ---: |
| normal home | 36.90 | 42.00 / 50.11 / 37.35 | **42.00** | 56.18 |
| normal stats_current | 46.19 | 41.20 / 45.65 / 27.84 | **41.20** | 47.31 |
| normal stats_past | 29.87 | 36.66 / 42.63 / 23.77 | **36.66** | 47.09 |
| heavy home | 29.49 | 39.19 / 40.61 / 36.63 | **39.19** | 51.11 |
| heavy stats_current | 31.72 | 38.96 / 31.65 / 32.33 | **32.33** | 42.50 |
| heavy stats_past | 32.90 | 41.66 / 31.87 / 29.63 | **31.87** | 41.72 |

p50 (2ms는 3회 중앙값):

| 시나리오 | 0ms | 2ms | 5ms | 0→2ms 증가 | 2→5ms 증가 |
| --- | ---: | ---: | ---: | ---: | ---: |
| normal home | 15.12 | 23.32 | 42.96 | +8.2 | +19.6 |
| normal stats_current | 15.88 | 20.43 | 35.91 | +4.6 | +15.5 |
| normal stats_past | 14.19 | 18.77 | 35.30 | +4.6 | +16.5 |
| heavy home | 20.26 | 28.06 | 42.02 | +7.8 | +14.0 |
| heavy stats_current | 18.85 | 23.66 | 35.10 | +4.8 | +11.4 |
| heavy stats_past | 19.45 | 23.16 | 34.98 | +3.7 | +11.8 |

- 모든 실행 실패율 0%.
- 2→5ms(왕복 약 2.5ms 증가)에서 p50 증가는 home 14–20ms, stats 11–17ms로, "추정 왕복 × 2.5ms"(home 약 15, stats 약 12.5)와 같거나 조금 크다. 이 구간에서는 왕복 지연이 대체로 응답 시간에 더해지는 것과 맞는다.
- 0→2ms(왕복 약 2.5ms 증가)의 p50 증가는 모델(home 약 15, stats 약 12.5)보다 작다. 0ms에서는 처리량이 높아(워밍업 포함 40초 요청 수 home normal 31,307건 vs 2ms 13,908–18,113건) 한 대에서 k6·앱·DB가 CPU를 더 다투기 때문으로 보이며, 원인은 분리하지 않았다.
- 같은 조건 3회 사이에도 p95가 크게 흔들린다(normal stats_current 27.84–45.65). 판정은 중앙값으로 했다.

## 캐시 효과 상한 (스텁, home, 2ms)

| 시나리오 | 구분 | p95 r1 / r2 / r3 | p95 중앙값 | p50 중앙값 |
| --- | --- | --- | ---: | ---: |
| normal home | 기준(위 표, 앞선 시간대) | 42.00 / 50.11 / 37.35 | 42.00 | 23.32 |
| | 기준 재측정(스텁 직후) | 27.89 / 28.23 / 26.61 | 27.89 | 20.00 |
| | 스텁 | 21.28 / 20.91 / 22.23 | 21.28 | 14.59 |
| heavy home | 기준(위 표, 앞선 시간대) | 39.19 / 40.61 / 36.63 | 39.19 | 28.06 |
| | 기준 재측정(스텁 직후) | 32.92 / 34.69 / 37.52 | 34.69 | 25.16 |
| | 스텁 | 19.98 / 20.70 / 20.96 | 20.70 | 14.67 |

상한 = 1 − 스텁 p95 / 기준 p95:

| 시나리오 | 앞선 기준 대비 | 재측정 기준 대비 |
| --- | ---: | ---: |
| normal home | 49.3% | 23.7% |
| heavy home | 47.2% | 40.3% |

- 앞선 기준과 스텁은 측정 시간대가 다르고(사이에 나머지 2ms·5ms 시나리오를 돌렸다), 같은 코드의 기준 normal home p95가 42.00 → 27.89로 바뀌었다. 시간대 차이가 결과를 크게 흔들기 때문에 **상한은 바로 이어 잰 재측정 기준을 쓴다**(normal 23.7%, heavy 40.3%).
- 스텁이 없앤 것은 왕복 1개(약 2ms)인데 p50은 normal 5.4ms, heavy 10.5ms 줄었다. 왕복 시간만으로는 설명되지 않는다. 처리량이 높아지면서 대기가 줄었거나(10 VU가 요청마다 트랜잭션 2개로 기본 풀 10개를 나눠 씀), heavy는 행 전송·매핑 비용도 빠진 것으로 보인다. 원인은 분리하지 않았다.
- 스텁은 "적중 비용 0인 캐시"이므로 실제 캐시는 적중 조회 비용·무효화 비용 때문에 이보다 효과가 작다.

## 판정

| 기준 (스펙 5절) | 결과 |
| --- | --- |
| 1. 2ms에서 홈·통계 p95 ≤ 50ms면 충분 | **만족.** 6개 시나리오 3회 중앙값 31.87–42.00ms 중 최대 42.00ms (한 회 값으로는 normal home r2 50.11ms가 50ms를 넘었다) |
| 2. 캐시 제안 = (50ms 초과) ∧ (p95 30% 이상 감소) ∧ (정합성) | **불만족.** 50ms 초과 시나리오가 없다 |
| 3. 상한 먼저 계산, 30% 미만이면 구현 생략 | normal 23.7%, heavy 40.3%. heavy는 30% 이상이지만 기준 1로 충분하므로 구현·정합성 검증은 생략 |
| 5. 5ms는 기록만, 50ms 초과 시 위험 기록 | **위험:** home normal 56.18, heavy 51.11ms. stats는 41.72–47.31ms |

따라서 **비채택**이다. 현재 런타임에 Redis 등 캐시 서비스는 필요하지 않다.

5ms 위험의 의미: 앱과 DB의 왕복이 5ms 안팎이면(예: 리전이 다르거나 풀러를 거치는 경우) 홈이 이 장비 기준 50ms를 넘는다. 이 경우에도 캐시가 줄이는 것은 왕복 6개 중 1개다. 실제 Cloud Run → Supabase(서울, 세션 풀러) 왕복은 재지 않았으므로 배포 후 확인한다.

## 캐시 외 개선 후보

**바로 PR 가능:** 없음. 기준 1을 만족하므로 지금 바꿀 측정 근거가 없다. 기존 결정과 충돌하지 않는 후보(커넥션 풀 크기 등)는 이번 측정에서 따로 재지 않았다.

**제안 (사용자 승인 필요, 손대지 않음):**

1. **인증 필터의 세션 확인 트랜잭션 정리** — 요청마다 `AuthService`의 읽기 전용 트랜잭션이 따로 있어 `COMMIT` 왕복이 1개 더 든다(home 약 6 중 1, stats 약 5 중 1). 줄일 수 있는 왕복 수는 월 합계 캐시 적중과 같다(1개). 다만 캐시 스텁의 p50 감소가 왕복 1개보다 컸던 원인(행 전송·매핑 등)은 이쪽에 없으므로 효과는 그보다 작을 수 있다. 다만 인증의 세션 확인 흐름(보안 동작)을 바꾸므로 스펙 5.4에 따라 제안만 한다. → 사용자 승인 후 진행: [세션 확인 트랜잭션 제거 전후 비교](2026-11-02-session-check.md).
2. **홈 월 합계를 SQL `SUM`으로 되돌리기(#35 결정)** — 스텁에서 heavy home p50이 왕복 1개보다 훨씬 많이(10.5ms) 줄어, 월 300건 행 전송·매핑 비용이 작지 않을 수 있다. `SUM`은 왕복은 그대로 두고 행 전송만 없앤다. 결정 전에 행 수별 `findAmounts` vs `SUM` 원인 분리 측정이 필요하다. 기준 1을 이미 만족하므로 급하지 않다.

## 확인하지 않은 것

- 실제 Cloud Run·Supabase 환경의 왕복 시간과 응답 시간.
- 사용자 200명보다 큰 규모, 다른 장비에서 부하 생성.
- 스텁 p50 감소가 왕복 1개보다 큰 원인(대기 감소, 행 전송·매핑, CPU 경합)의 분리.
- 커넥션 풀 크기 변경의 효과.
