# 2026-11-02 홈 월 합계: 행 조회 vs SQL `SUM`

> **비채택. #35 결정(행 조회 → Service 집계)을 유지한다.** DB 왕복 약 2ms에서 home p95(3회 중앙값)는 행 조회와 `SUM`이 같은 수준이었다(normal 19.05 / 19.95ms, heavy 19.17 / 19.56ms). 차이는 지연 0에서 앱·DB·k6가 한 장비 CPU를 다투는 heavy에서만 나타났고(p95 중앙값 15.45 → 7.86ms), DB·전송 구간 차이는 작아 앱 쪽 행 처리 비용으로 추정된다(프로파일링하지 않음).

배경: [월 합계 캐시 실험](2026-11-02-cache-experiment.md)의 제안 2. [#35 측정](2026-10-27-monthly-spending.md)에서 heavy home이 `SUM` 대비 2.07배 느렸으나 원인을 분리하지 않았다. 사용자가 측정 결과를 보고 #35 유지를 결정했다.
원본 출력: `2026-11-02-home-sum/pgbench/`(쿼리 스크립트와 결과), `2026-11-02-home-sum/latency/2ms.txt`(지연 확인), `2026-11-02-home-sum/k6/`(k6 summary JSON, `setup_data` 제거)

## 방법

- 기준: develop `cce35f2`(포트 8090), `findAmounts`로 행을 받아 `MonthlySpending`에서 합산.
- 스텁: 같은 커밋에서 `HomeService`만 `SELECT COALESCE(SUM(amount), 0)` 한 문장으로 바꾼 로컬 브랜치(포트 8091, push하지 않음). 스텁에서도 `HomeApiTests`는 통과했다.
- 장비·도구·데이터는 [캐시 실험](2026-11-02-cache-experiment.md)과 같다(Apple M2, 측정 DB tmpfs, toxiproxy 2.12.0, 사용자 200명 × 12개월, VU 10, 워밍업 10초 + 측정 30초). 두 앱을 같은 측정 DB·프록시에 동시에 연결했다.
- 원인 분리용으로 측정 DB에만 이번 달 지출 1,000건·3,000건인 합성 사용자 2명을 더했다(k6에는 쓰지 않음).

## DB·전송 구간 (pgbench, 클라이언트 1개, 15초, latency average ms)

두 쿼리를 프록시를 거쳐 직접 보냈다. 행 조회는 결과 행 전송까지 포함하고 앱의 객체 변환은 포함하지 않는다. 2회차는 쿼리 순서를 바꿨다.

| 30 | 0.157, 0.156 / 0.158, 0.156 | 2.628, 2.926 / 2.664, 3.015 |
| 300 | 0.209, 0.205 / 0.173, 0.172 | 2.783, 3.158 / 2.669, 3.003 |
| 1,000 | 0.298, 0.298 / 0.197, 0.197 | 3.128, 3.412 / 2.767, 3.136 |
| 3,000 | 0.680, 0.664 / 0.339, 0.339 | 3.885, 4.062 / 3.605, 3.509 |

- 월 300건에서 행 조회가 `SUM`보다 0.03–0.16ms, 3,000건에서도 0.28–0.55ms 더 걸릴 뿐이다. DB 실행과 행 전송만으로는 #35의 heavy 차이(p95 26.71 − 12.92 = 13.79ms)를 설명할 수 없다.

## 해석

- DB·전송 구간 차이는 위 표처럼 작으므로, 남은 차이는 앱 쪽 행 처리(JDBC 디코딩·객체 변환·합산) 비용으로 추정된다. 프로파일링은 하지 않았다.
- 이 차이는 앱·DB·k6가 한 장비 CPU를 다투는 지연 0 heavy에서만 응답 시간과 처리량 차이로 드러났다(CPU 사용률은 기록하지 않음). 왕복 약 2ms에서는 요청 대부분이 DB 응답을 기다리는 시간이라 차이가 없었고, `SUM`의 p95는 6쌍 모두 행 조회보다 0.20–1.04ms 높아 더 빠르지도 않았다. normal(월 30건)은 2ms에서 차이가 없고, 지연 0에서는 p95가 비슷하며 요청 수만 `SUM`이 약 5% 많았다(2회).
- 기준 1(왕복 약 2ms에서 p95 ≤ 50ms)을 이미 만족하고, 월 300건 이상 사용자는 드물 것으로 가정한다(실제 분포는 확인하지 않음). `SUM`으로 바꾸면 #35에서 정한 구조(AGENTS.md "합계·카테고리 집계는 Service의 도메인 객체에서 계산한다")에 홈만 예외가 생긴다. 그래서 바꾸지 않는다.
- 다시 볼 조건: 배포 후 인스턴스 CPU가 포화되거나, 월 지출 건수가 많은 사용자의 home 지연이 기준을 넘을 때.

## 확인하지 않은 것

- 앱 안에서 행 변환과 합산 중 어느 쪽이 큰지(프로파일링하지 않음).
- stats·목표 화면(같은 `findAmounts`를 쓰지만 카테고리 집계가 필요해 이번 대상이 아님).
- 실제 Cloud Run·Supabase 환경.
